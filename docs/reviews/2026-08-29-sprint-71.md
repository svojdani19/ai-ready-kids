# Sprint 71 — a school operation and its audit entry were two facts

**Date:** 2026-08-29
**Reviewed against:** HEAD `0a09050`
**Scope:** the four class operations. No schema change, no student data, no
change to authorization, subscription, licence, classroom-cap, privacy or
retention rules.

## The finding

Three surfaces sell the same promise:

| Surface | Says |
| --- | --- |
| Public `/privacy` | *"Every configuration change and every deletion writes an audit entry naming who did it and when."* |
| Admin Audit log | *"Every configuration and deletion action, with who did it and when."* |
| Plans | an audit log of every configuration change |

All four class operations mutated first and audited afterwards, each write
committing separately. When `recordAudit` failed:

- **Delete** had already cascade-removed the class, roster, attempts, check-ins
  and assignments — and the administrator saw an unhandled failure over a class
  that no longer existed, with no `data.deleted` entry to show for it.
- **Archive** had already rotated the code and signed the room out (sprint 69),
  unrecorded.
- **Rotate** had already invalidated the credential, unrecorded.
- **Restore** had already reactivated the roster, unrecorded.

Someone reading the audit log to answer *"who deleted Room 12, and when"* would
have found nothing while Room 12 was gone. That is a data-governance and
credential-recovery defect, not a logging gap.

## The correction

`src/lib/repo/audited.ts` → `auditedWrite(db, write, audit)`: one
`BEGIN IMMEDIATE`, the mutation, the audit insert, commit — or rollback. The
repository operations check `db.isTransaction` and participate, so nesting is
safe, and a test pins that rather than assuming it.

Each action wraps its mutation and returns a calm inline error when the write
fails, naming the state that did not change:

| Operation | On failure |
| --- | --- |
| Delete | *"Room 12 was not deleted, and **no records were removed**: the roster, every mission attempt, both check-ins and the class itself are all exactly as they were. Nothing was written to the audit log either. Try again…"* |
| Archive | *"…still active, its join code is unchanged, and anyone signed in to it stays signed in."* |
| Restore | *"…still archived, its join code is unchanged, and none of its records have changed."* |
| Rotate | *"…The current code still works and nobody has been signed out."* |

None promises support, monitoring or diagnostics — sprint 70's lesson, now a
test that forbids `account contact`, `contact us/support`, `support`, `we will
look/investigate/fix`, a response time, `logged` and `diagnostic` in all four.

**Restore refusals are untouched.** A plan, classroom-cap or licence refusal
throws out of `restoreClass` *before* anything is written, so the transaction
rolls back a nothing; the refusal audit is then recorded on its own afterwards,
because those entries record that nothing happened and must survive. They are
not collapsed into the operational-failure message.

**`deleteClassDataAction` now returns `{ error?: string }`** instead of `void`,
and both call sites `return` it instead of awaiting and discarding — so
`ConfirmAction` has something to render. That mattered most here: the deletion
could already have happened while the administrator saw a crash.

## Failing-before

`tests/audited-writes.test.ts` installs a `BEFORE INSERT` trigger on `audit_log`
that raises `ABORT` for one action — exactly the described failure: the mutation
has executed and the record of it cannot be written. The trigger touches nothing
else, so anything that survives is the operation's own doing.

Run against the pre-sprint-71 sequence (same helper body, mutate-then-audit),
**4 of 15 fail** — one per operation:

```
× delete:  an audit failure leaves the database exactly as it was
× archive: an audit failure leaves the database exactly as it was
× rotate:  an audit failure leaves the database exactly as it was
× restore: an audit failure leaves the database exactly as it was
```

The delete diff shows the class present in the expected snapshot and absent in
the received one — 23 children's records gone, with `data.deleted` audits at 0.

## Correction during acceptance — two tests did not prove what they claimed

### 1. The retry assertions could not fail on a no-op

The retry table asserted one thing per operation, and for two of them it was the
**precondition**:

```ts
rotate:  assertDone: () => expect(getClass(db, DEMO_CLASS)!.archived_at).toBeNull()
archive: assertDone: () => expect(getClass(db, DEMO_CLASS)!.archived_at).toBeTruthy()
```

`rotate` never checked that the code changed — `archived_at` stays null whether
`rotateJoinCode` rotates or does nothing at all. `archive` checked the timestamp
and not the rotation, which is **half the credential boundary sprint 69 built**:
`archiveClass` could stop issuing a new code and this test would still pass.

Replaced with `assertRetry(before)` per operation, where `before` is captured
**before the failed attempt** so the comparison spans both:

| Operation | Asserted |
| --- | --- |
| **rotate** | `join_code` differs; `archived_at` still null; every other class column identical; all protected records identical |
| **archive** | `archived_at` non-null (and was null before); `join_code` differs; every other class column identical; all protected records identical |
| **restore** | `archived_at` back to null (and was non-null); `join_code` **byte-identical** — restoring does not un-rotate the archive's code; every other class column identical |
| **delete** | class row gone, roster gone, real cascade proof, other classes and the school untouched |

"Every other column" is `classExcept(row, ...allowed)`, which strips only the
columns that operation may change and compares the rest — so "it changed
something" cannot pass for "it changed the right thing". Protected records are
every student, attempt, check-in, assignment, the school, and every *other*
class.

**Shown to fail on a deliberate no-op**, which the old assertions did not:

```
rotateJoinCode returns a code without writing it
  × rotate: the retry makes exactly the intended change, and one audit entry

archiveClass sets archived_at without rotating the code
  × archive: the retry makes exactly the intended change, and one audit entry
```

### 2. The refusal test manufactured its own evidence

It called `restoreClass` directly, watched it throw, and then **wrote the
refusal audit row itself**:

```ts
auditedWrite(db, () => {}, () => ({ action: "class.restore_blocked_by_licence", … }))
```

So it asserted that a row it had just inserted existed. It would have passed
unchanged if `restoreClassAction` had stopped writing refusal audits altogether
— which is precisely the regression it was meant to prevent.

Replaced with four tests that call the **exported `restoreClassAction`** against
a real seeded database and a real administrator session (`writeSession` with
`DEMO_ADMIN`, `next/headers` mocked to a cookie jar, `globalThis.__airkDb`
pointed at the fixture). Nothing in them creates an audit row.

| Path | Asserted |
| --- | --- |
| Over the licence | the established inline message (*"licensed places are already in use… stays archived and none of its records have changed"*), **not** the operational-failure one; class row and all protected records identical; exactly one `class.restore_blocked_by_licence`; zero `class.restored`; total audit count up by exactly one |
| Over the classroom cap | message names the classroom plan; nothing changed; exactly one `class.restore_blocked_by_plan` |
| Unrecognised plan | message does not echo the stored value back (sprint 53's rule); nothing changed; exactly one `class.restore_blocked_by_plan_config` |
| With seats available | restores, `join_code` unchanged from the archived state, exactly one `class.restored` |

**Shown to fail when the four refusal `recordAudit` calls are stripped from the
action:**

```
× refuses over the licence, changes nothing, and writes only its refusal audit
× refuses over the classroom cap, changes nothing, and writes only its refusal audit
× refuses an unrecognised plan, changes nothing, and writes only its refusal audit
    AssertionError: expected [] to have a length of 1 but got +0
```

## Known gaps

- **Failures still write nothing.** A rolled-back operation leaves no trace, by
  the same reasoning as sprint 70 — but it means an administrator who retries
  successfully has an audit log showing one clean operation and no sign that the
  first attempt failed.
- **`revalidatePath` runs after the transaction and is not part of it.** If it
  threw, the write would already be committed. It does not touch the database
  and its failure would be a framework problem, not a data one, but the
  atomicity claim stops at the commit.
- **The wrapper is per-action, not a general rule.** Nothing prevents a future
  action from mutating and auditing separately; the buyer-promise test checks
  the four that exist today by name, and would not notice a fifth.
- **Non-class operations are unchanged.** `setRetentionAction`,
  `setAcademicDatesAction`, staff removal and the report export still audit
  outside a transaction. They are configuration writes rather than cascading
  deletions or credential rotations, so the consequence of a lost entry is
  smaller — but it is the same shape, and it is not fixed here.
