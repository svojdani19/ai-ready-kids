# Sprint 70 — the school-year rollover was four commits pretending to be one

**Date:** 2026-08-29
**Reviewed against:** HEAD `4d447b0`
**Scope:** make the rollover atomic and recoverable. No student data, no scope
broadening, no schema change.

## The finding

`rolloverYearAction` performed a sequence of **independently committed** writes:

```
for (const c of preview.toArchive) archiveClass(db, c.id);   // commits per class
setAcademicYear(...)                                          // commits
setBenchmarkWindow(...)                                       // commits
recordAudit(...)                                              // commits
```

`archiveClass` opens its own `BEGIN IMMEDIATE` when there is no outer
transaction, so each class committed on its own. A failure on the second class —
or on any later write — left the school half transitioned: some cohorts archived
and their join codes rotated, others still active, the academic dates still last
year's, the check-in window in whatever state it had reached, and no trustworthy
audit row either way.

**Sprint 69 raised the cost.** Archiving now rotates a class's join code, so a
partial rollover does not merely mislabel a class — it hands out new credentials
for some rooms and not others, signing those children out, with nothing
recording which.

## The correction

`src/lib/repo/rollover.ts` → `performRollover(db, schoolId, actorLabel)`, one
`BEGIN IMMEDIATE` covering all of it, and the action reduced to calling it.

Two things make it atomic rather than merely wrapped:

1. **`BEGIN IMMEDIATE` takes the write lock up front**, so the read the decision
   is made from cannot be overtaken between reading and writing.
2. **The school and classes are re-read inside the transaction** and the preview
   recomputed there. The page's preview stays informational and may be seconds
   stale; the one the mutation acts on is transactional. This was the stale-
   preview requirement, and it is why `previewRollover` is now called twice —
   once for the page, once decisively.

`archiveClass` already honoured an outer transaction (`db.isTransaction`), so it
participates instead of committing around it — a property now pinned by its own
test rather than assumed.

A refusal from the preview (unreadable academic dates) rolls back and returns
`{ ok: false, error }` **before any write**; a thrown failure rolls back and the
action returns `ROLLOVER_FAILED` as an inline error, keeping the retry path
rather than leaving a 500 for an expected operational failure.

The audit row is written **inside** the transaction, so a later failure takes it
with it: exactly once on success, never on failure.

The message is only made because the rollback proves it:

> The rollover did not finish, so nothing was changed: every class, code, date
> and check-in window is exactly as it was before you pressed the button. Try
> again, and if it keeps happening your account contact can look at it.

## Failing-before

`tests/rollover-atomicity.test.ts` injects a **SQLite trigger** that counts
archives in a temporary table and raises `ABORT` on the second — so the first
`UPDATE classes SET archived_at = …, join_code = …` succeeds and the next
aborts. That is the exact shape of the defect: partway through the class loop,
credentials already rotated. The test asserts the fixture has **at least two**
classes to archive, so "after the first write" cannot be vacuous.

Run against the pre-sprint-70 sequence (the same function body, un-transacted),
**3 of 4 fail**:

```
× rolls back the archives and codes already written
    AssertionError: expected 1 to be +0
× reports the failure to the caller as an error rather than a crash
× succeeds cleanly on the retry once the failure is removed
```

`expected 1 to be +0` is the counter row surviving the abort — proof the first
archive **committed independently** rather than inside the caller's transaction.
And the snapshot diff shows the partial state in full:

```
- Room 4 … "archived_at": null,  "join_code": "ACORN-BADGER-208"
+ Room 4 … "archived_at": "2026-08-29T11:46:19.286Z", "join_code": "BUTTON-HERON-775"
```

Room 4 archived and its code rotated; Rooms 12, 14 and 21 still active on their
old codes; the school year still `2025-2026`; no audit row. One room's children
signed out, three rooms' not, and nothing recording it.

After the fix all four pass, and the trigger's own counter is gone after the
rollback — the write really was inside the transaction.

## Remaining gaps

- **The page preview can still be stale**, by design. It is informational; the
  action re-reads. An administrator can therefore see "4 classes archived" and
  have the transaction act on 3 if someone archives one meanwhile — the result
  message reports what actually happened, not what the preview predicted.
- **`ROLLOVER_FAILED` is one message for every failure mode.** A disk error, a
  lock timeout and a constraint violation all read the same to the
  administrator. That is deliberate — none of them is actionable by a school —
  but it means the audit log holds nothing about attempts that failed, so a
  repeatedly failing rollover leaves no trace for support to read.
- **Nothing retries automatically**, and nothing queues. If the failure is a
  transient lock, the administrator presses the button again.
- **The rollover is still the only multi-write action wrapped this way.**
  `restoreClass` and `archiveClass` have their own transactions, but no audit
  is inside them, so a failure after `recordAudit` in `archiveClassAction` would
  still leave an archive with no audit row. Narrower, same shape, not fixed here.
