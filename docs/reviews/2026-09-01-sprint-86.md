# Sprint 86 — the guard's coverage was a list, and the list was wrong

**Date:** 2026-09-01
**Reviewed against:** HEAD `58cee66`
**Scope:** `tests/program-scope.test.ts` only. **No product code changed**, no
schema, no field, no copy. A mechanism fix to the guard sprint 85 built.

## The finding

Sprint 85 ended with this at the top of its own gaps list:

> The derivation is structural; "no surface attaches 1–5 to what is sold" is a
> pattern over seven named files. A surface added tomorrow is not in the list.

That understated it. The list was not merely incomplete for the future — it was
**already wrong by four of eight marketing pages**:

| Covered | Not covered |
| --- | --- |
| `approach`, `curriculum`, `plans`, `for-schools` | **the marketing home page**, `demo`, `benchmark`, `privacy` |

The home page is the most-read buyer surface in the product and no scope guard
ran over it at all.

**This is the defect that produced the last three corrections.** The curriculum
hero kept offering "a grade 1 or grade 5 class" through three consecutive
passes because each sweep covered the surfaces its own finding named, and the
list never grew to match. Sprint 85 wrote the lesson down —
*"the sweep that missed this was a grep over named files"* — and then left the
guard as a grep over named files.

**Today it is latent, not live.** All four unguarded pages were read: none makes
a grade-scope claim, and `demo`'s "Grade 2 / Grade 3 / Grade 4" mentions are
inside the band and correct. So this sprint fixes the mechanism, not a live
buyer-facing lie.

## The correction

The marketing route group is **walked from disk**:

```ts
const BUYER_SURFACES = [
  ...NON_ROUTE_SURFACES,
  ...marketingPages("src/app/(site)", "src/app/(site)").sort(),
];
```

Coverage goes from **7 hand-written paths to 14 surfaces** — nine `page.tsx` and
`layout.tsx` files under `(site)`, plus five that cannot be enumerated from the
route group and are therefore still named: `README.md`, the root `layout.tsx`,
`SiteHeader`, `SiteFooter` and `marketing/Page.tsx`.

Both existing guards — the annual-range one and the uncreatable-class one from
sprint 85's third correction — now run over all fourteen. A page added tomorrow
is checked the day it exists.

The five named files are **asserted to exist**, so a rename cannot silently drop
one from the guard. That is the failure mode a named list has that a walk does
not, and it is worth a test rather than a comment.

## Demo data: a row I left behind, and a sweep that would not have found it

Before committing I checked the demo database and found it **had drifted**:
audit log 7 and assignments 66, where the last three sprints each verified 6 and
65.

The extra rows were one `mission.assigned` — *"The Study Group assigned to Room
12"* — and its assignment row, timestamped `2026-08-31T15:46:38Z`, during the
sprint 85 eligibility browser pass. Mine, and left behind. Both removed; the
database is back to audit log 6, assignments 65, Room 12 at its seeded 21
assignments.

Two things worth recording rather than glossing:

**The end-of-sprint sweep reported zero recent rows and this row is dated inside
that range**, so it was written after the sweep ran. That is the flaw in the
check itself: it runs once, before the browser session is actually finished, and
proves nothing about what happens next. A restore check that precedes the last
interaction is a check of the wrong moment.

**The sweep's column filter was sloppy.** It matched `/_at$|^created|^started|^completed|^assigned/`,
and `^assigned` catches `assigned_by` — a user-id column, not a timestamp. With
the `like '2026-08-3%'` pattern it produced no false positives by luck, because
`usr_okafor` never matches a date prefix; the moment I used a `>=` range
comparison it reported all 65 assignments as recent. The sweep now walks only
columns ending `_at`, and prints which twelve it checked:

```
schools.created_at, users.created_at, classes.created_at, classes.archived_at,
students.created_at, assignments.assigned_at, attempts.started_at,
attempts.completed_at, benchmarks.started_at, benchmarks.completed_at,
certifications.completed_at, audit_log.created_at
```

Zero rows dated 2026-08-30 or later across all twelve.

## Known gaps

- **The restore check is still a habit, not a mechanism.** Nothing in the
  repository compares the demo database against its seeded state; it is a script
  I write from memory at the end of a sprint, which is exactly how the row above
  survived. A `npm run demo:verify` that diffs against a seeded snapshot would
  make it real.
- **`NON_ROUTE_SURFACES` is still five hand-written paths.** They cannot be
  walked from the route group, so the list is unavoidable — but a sixth
  buyer-facing component added outside `(site)` would be unguarded, and only the
  existence check protects the five that are there.
- **The guards are still regexes over source text.** Enumeration fixed *which
  files* are checked, not *how well*. A scope claim phrased outside both patterns
  passes on all fourteen surfaces.
- **`layout.tsx` files under `(site)` are swept as buyer surfaces.** That is
  deliberate — a layout can carry copy — but it means the walk's file filter is a
  judgment about what counts as a surface, and it is stated in one line of code
  rather than tested.
