# Sprint 46 — the same menu, two different ways out

**Date:** 2026-08-28
**Scope:** the mobile half of the keyboard exit sprint 45 documented and left.
Shared navigation only.

## The finding

Sprint 45 gave the desktop disclosure a complete keyboard exit: Escape closes it
and returns focus to the trigger. It left the responsive panel alone, and said
so. The result was one navigation with **two different escape behaviours,
decided by nothing but window width**.

At 768×1024 that panel covers most of the screen. A keyboard or switch user
could only close it by finding and activating the Menu button again — from
inside a panel that had just taken over the viewport. A pointer user taps the ✕
without thinking about it.

For a school accessibility review this is the harder version of sprint 45's
defect, because it is not an oversight in one handler; it is the same control
being accessible at one size and not at another. That is difficult to defend in
a procurement conversation and impossible to defend to the person using it.

## What changed

Escape now closes the responsive panel and returns focus to the Menu trigger,
using the same two guards as the desktop menu plus one the viewport requires.

```ts
const insidePanel = Boolean(mobilePanel.current?.contains(document.activeElement));
setMobileOpen(false);
if (insidePanel && isRenderedVisible(mobileTrigger.current)) {
  mobileTrigger.current?.focus();
}
```

- **Focus must be inside the panel.** Escape never pulls focus back from
  wherever the user has already moved it. This is also the rule that makes the
  resize case safe, since focus cannot be inside a panel CSS has removed.
- **The trigger must be genuinely rendered.** The panel and its button are
  `lg:hidden`. A panel state that survives a resize to desktop leaves both
  hidden, and refocusing a button nobody can see would be sprint 45's trap in a
  new place. The state is still cleared, which is the safe reset.
- **Escape is ignored entirely while the panel is closed** — the effect does not
  subscribe.

Everything else is untouched: link activation still closes without pulling focus
back, toggling the button keeps ordinary browser focus, and the desktop
`NavMenu` behaviour from sprint 45 is unchanged.

### The visibility check, and why it degrades

```ts
function isRenderedVisible(el: HTMLElement | null): boolean {
  if (!el) return false;
  const check = (el as HTMLElement & { checkVisibility?: () => boolean }).checkVisibility;
  return typeof check === "function" ? check.call(el) : true;
}
```

jsdom does no layout: `offsetParent` is always `null` and `checkVisibility` does
not exist. A naive check would report every element invisible under test and
silently disable the recovery the tests exist to verify. So it falls back to
trusting the focus-location guard, and the viewport behaviour is verified in a
real browser instead — where it is a CSS breakpoint, which is the only place it
means anything.

## Tests

Eight added to `tests/site-header.test.tsx`, eighteen in the file. **Five were
confirmed to fail without the fix** by stashing the component.

- Escape with a panel link focused closes it, hides the panel, and returns focus
  to the Menu trigger, with the link neither focused nor visible;
- focus already moved elsewhere: the panel may close, focus stays put;
- Escape while closed does nothing at all;
- choosing a link closes without pulling focus back;
- toggling the trigger leaves ordinary focus alone;
- it keeps working on a second open, and a second Escape neither reopens nor
  double-closes;
- **desktop regression**: closing the panel leaves the desktop triggers exactly
  as they were, and the desktop menu still escapes on its own terms afterwards.

Worth recording: jsdom renders both the desktop and the mobile markup, because
the split is a CSS breakpoint and there is no CSS in these tests. That is what
lets them drive the panel directly, and it is why the resize trap is asserted
through the focus-location rule here and checked properly in the browser.

**531 tests, up from 523.**

## Verified in the browser

**768×1024, keyboard only.** Menu focused and opened, ten links in the panel,
focus put on *Annual check-ins*, `focusInsidePanel` true. Escape →
`aria-expanded="false"`, panel hidden, focus on the Menu trigger and
`checkVisibility()` true. Tab from there reaches *See the demo*, visible. No
horizontal overflow.

**The resize trap, exercised for real.** Opened the panel at 768×1024, resized to
1280×800. The mobile trigger and panel both report `checkVisibility() === false`
while the state was still `true`. Opening the desktop menu, focusing a link and
pressing Escape then gave: desktop menu closed, **focus on the desktop trigger
and visible**, focus **not** on the hidden mobile trigger, and the stale mobile
state reset to `false`. Both halves of the guard doing their job.

**1280×800.** Desktop behaviour unchanged from sprint 45.

## Out of scope

No curriculum, subscription, child-data or marketing-claim change. Shared
navigation only.

## Observed, not changed

**The panel has no click-outside dismissal**, unlike the desktop menu, which
uses `useDismiss` for pointer and focus-out as well. Adding it was not asked for
and would change pointer behaviour that nobody has reported a problem with, so
the mobile handler deliberately does Escape and nothing else. If it is added
later it should go through the same reason-aware path rather than a second
mechanism.

## The lesson

**Responsive variants are separate implementations, and accessibility does not
inherit across a breakpoint.** Sprint 45 fixed a keyboard exit and wrote "mobile
unchanged" as a scope note; what that actually described was the same product
being usable at one width and not another. When a fix lands on one side of a
media query, the question is not whether the other side was in scope — it is
whether the other side is now worse by comparison.
