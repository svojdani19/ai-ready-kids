# Sprint 34 — P0 follow-up: the schema gate

**Scope.** One issue, the gate only. The finding was correct, and it identified
a state my own review text described without ever testing.

---

## What was wrong

Sprint 33's `storedVersion` returned `null` for two different situations:

- there is no `meta` table, because the file is brand new; and
- `meta` exists and holds no `schema_version` row.

The second is not hypothetical. **The pre-sprint-33 `db:reset` produced it.**
That command opened a database and then ran `DELETE FROM meta WHERE key <>
'session_key'`, so any database reset with it holds a complete set of tables and
every row of data, and no recorded version at all.

Sprint 33 read that as a new file: applied `CREATE TABLE IF NOT EXISTS`, which
adds no columns, stamped version 2, and returned a database that claimed to be
current and failed on the first query touching a sprint-32 column. Exactly the
failure sprint 33 existed to prevent, reached by a different door.

There is a second route to the same state, which the finding did not need to
name and which makes it more likely rather than less: a **sprint 32** database
had the v2 shape while `SCHEMA_VERSION` still said `"1"`, so a reset in that
window produced a v2-shaped file with no version either.

And my own sprint 33 review text noted that reset used to delete the version.
The test inserted `'1'` every time, so it never met the thing the prose
described.

## The gate

`classifySchema` inspects `sqlite_master` and the actual columns **before** the
schema is applied, and returns one of four things:

- **`empty`** — no user tables at all. Create and stamp latest.
- **`versioned`** — a version row that parses strictly as a whole number, is at
  least 1, is not above `LATEST_VERSION`, **and whose claimed version matches
  the shape actually present**.
- **`unversioned`** — no version row, but the columns positively identify a
  known version. Stamped with the version its shape has, then migrated forward
  like any other.
- **`unrecognised`** — everything else.

Recognition is positive, not by elimination. Version 1 requires the sprint-27
`schools.benchmark_window` **and** the absence of the sprint-32 columns; version
2 requires all four sprint-32 columns. A database older than the v1 fixture
matches neither and is refused rather than half-migrated.

**Unrecognised fails closed.** The file is not touched, the handle is closed,
and the error names what was found and what to do: take a copy first, since it
is one file and a copy is a complete backup; run the newer build rather than
downgrading if that is what happened; otherwise restore a backup, or reset if
the contents are demo data.

Refusing to open is the safe direction. The data is still there and a person can
look at it — which is more than could be said for a database that was stamped
current and then started throwing on every page.

## Tests

Eight more, sixteen in the file. The fixture builder takes the version to write,
and **`null` reproduces the old reset state** — complete v1 data, `session_key`
retained exactly as that command left it, no `schema_version`.

- That state is classified `{ unversioned, version: 1 }` by its shape, migrated,
  and stamped 2 — with a precondition assertion that the version row really is
  absent and the data really is there first.
- Everything survives it: class, roster, `evidence_json`, assignment, benchmark,
  certification, audit row. **A query touching a new column works**, which is
  the thing that used to fail.
- A sprint-32-shaped database with the version deleted is recognised as
  `{ unversioned, version: 2 }` and stamped without migrating.
- An empty file is still `empty` and stamped latest.
- A partial schema is refused, and the message says nothing was changed.
- Malformed versions are refused rather than coerced: `two`, `2.5`, `-1`, `" "`,
  `0`, `2abc`.
- A version above `LATEST_VERSION` is refused with the newer-build guidance.
- A database claiming version 2 with version 1 columns is refused, **and the
  file is checked afterwards to confirm nothing was written on the way out**.

The conservative retention backfill is unchanged, and so is every student and
privacy constraint.

**456 tests, up from 448.**

### Verified outside the suite

Built the old reset state by hand — v1 schema, `session_key` present,
`schema_version` absent, linked school/teacher/class/student/attempt — and
opened it through `openDatabase`: version 2, session key still there, roster and
evidence intact, `year_ends_on` empty as designed. A malformed file produced the
refusal with its guidance and left the file alone.

## What this says about the review process

Sprint 33 replaced an unconditional write with a read, which was the right
change, and then implemented the read as a function that could not tell two
states apart. **A boolean answer to a question with three states is a bug
waiting for the third state**, and the third state was documented in the same
sprint's own review text.

The narrower version, worth keeping: `null` was doing duty for both "absent" and
"nothing there". Where a return value has to distinguish more than two
situations, it needs a type that can, and the compiler will then insist every
one is handled.

## Deliberately left

- **Only one previous shape is recognised**, the v1 fixture. Anything older
  fails closed, which is correct — this build has no evidence about what those
  files contain — but it does mean there is no upgrade path from before that.
- No down-migrations. Forward only.
