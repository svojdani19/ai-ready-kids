# Sprint 33 — P0: an upgrade that destroyed the data it was upgrading

**Scope.** One issue, the infrastructure fix, nothing else. The finding was
correct and the severity was right.

---

## What was wrong

Sprint 32 added four required columns — `schools.academic_year`,
`year_starts_on`, `year_ends_on` and `classes.year_ends_on`. `openDatabase` ran
`CREATE TABLE IF NOT EXISTS` and then wrote `schema_version = 1`
**unconditionally, without ever reading it**.

`IF NOT EXISTS` creates missing *tables*. It does nothing whatever about missing
*columns*. So on any existing database the columns simply did not appear, the
version row claimed the schema was current, and the first query touching a new
column failed. The README's answer was to delete `data/airk.db`.

For a school subscription that is every roster, every authored-choice attempt,
every skill record, every badge and both check-in windows — and it contradicts
the retention story the product sells on its own privacy page. There is no
version of "delete your students' work to install the update" that is
commercially viable.

## The migration path

`src/lib/db/migrations.ts` holds an ordered list. `openDatabase` now:

1. **Reads** the stored version before writing anything. A brand-new file has
   no `meta` table and is stamped at the latest version, so no migration runs
   against a schema that is already current. An existing file is migrated from
   whatever it actually records.
2. Runs each pending migration **in its own transaction**, with the version row
   written **inside that transaction**. SQLite DDL is transactional, so a
   failure rolls back the columns and the version together and the error stops
   the process. There is no state where half a migration has been applied and
   the version says it worked.
3. Is idempotent by construction — a migration runs only when the stored
   version is below it, and `addColumn` checks `PRAGMA table_info` first.

`db:reset` now **preserves** `schema_version`. It had been deleting it along
with everything else, which was harmless only while the opener rewrote the
version unconditionally; with a real migration path, dropping it would make the
next open mistake an old database for a new one and skip the migration
entirely. The README now says plainly that reset is demo data and not an
upgrade path.

## The backfill, and why it records nothing

The finding said to stop and report if a safe legacy date backfill needed a
product decision. It does not, because the finding itself names the correct
answer and it is the conservative one.

Nothing in the old schema records when a school year ended. `class.school_year`
holds a **label** — "2025-2026" — and a label is not a date: districts finish in
May, June or July. The renewal date is available and is exactly the wrong
answer; in the seed it is 1 September, three months after a normal year end,
and sprint 32 existed to stop it being used for this.

Guessing early deletes a child's records before the school's own window has
elapsed. Guessing late holds them past the policy the school set. **Neither is
this code's decision to make on a school's behalf**, so the migration:

- carries forward `academic_year` from the most recent class label, which the
  old data does say accurately;
- leaves `year_starts_on`, `year_ends_on` and every class's `year_ends_on`
  **empty**.

Empty means *not recorded*, and retention treats it as blocked rather than due:
`purgeDateForClass` returns null, `retentionRows` reports `eligibleNow: false`,
and `runScheduledPurge` skips those cohorts. A test runs the job in 2099 against
a migrated database and asserts nothing is deleted. **Unknown is not the same as
due.**

An administrator supplies the real dates on Program & plan, which backfills the
cohorts in that year in the same operation. The panel says why they are missing
rather than presenting an empty field with no explanation.

## Tests

Eight, in a new `tests/migration.test.ts`, built on `tests/fixtures/v1-schema.sql`
— the **literal** pre-sprint-32 schema extracted from the commit before it, so
the test cannot drift into asserting against the current shape.

The fixture database holds one of everything, linked: school, staff user, class,
student, assignment, attempt with a real path and evidence map, benchmark,
certification, audit row. Opened through the ordinary `openDatabase` path.

- New columns present, version advanced to 2.
- **Every record and every link survives** — join code, teacher id, display
  name, avatar, the attempt's `path_json` and `evidence_json` intact, and a row
  still present in each of assignments, benchmarks, certifications, audit_log
  and users.
- The year label carried forward; the dates empty; and specifically
  `year_ends_on !== term_renews_on`, because borrowing the renewal date is the
  tempting wrong answer.
- Retention blocked: null due date, not eligible in 2099, purge deletes nothing.
- Re-running is a no-op, with the column not duplicated.
- **A forced failure rolls back**: version still 1, the added column gone, the
  student row untouched.
- A brand-new database is stamped at the latest version without migrating.
- A demo reset keeps the version.

**448 tests, up from 440.**

### Verified outside the suite

Built a version-1 database by hand with Brightwood's real ids, opened it through
`openSeededDatabase`: version 2, `academic_year` 2025-2026, both date fields
empty, student and attempt evidence intact. Then cleared the dates in the demo
database to reproduce the migrated state in the running app — the retention page
reads **"Not set — Record when the school year ends on Program & plan. Nothing
is deleted until you do."** Supplying the dates through the form backfilled all
four classes.

## What this says about the review process

The defect was created by the sprint that added the columns, and every one of
the 440 tests passed. They all built their databases from the current schema, so
none of them had ever seen an old one — the same blind spot as sprint 32, one
layer down. That sprint's lesson was "is this correct the second time"; this is
the same question asked of the schema rather than the calendar.

The other thing worth naming: `schema_version` existed the whole time and was
being written without being read. **A version that is stamped rather than
checked is worse than no version at all**, because it makes an out-of-date
database claim to be current, and everything downstream believes it.

## Deliberately left

- **No down-migrations.** Forward only. A rollback means restoring the file,
  which is why the README now says to back it up first — it is one file.
- **The rest of sprint 32's UI** is untouched, and the unrelated gaps in the
  handoff are still there.
