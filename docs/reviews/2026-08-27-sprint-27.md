# Sprint 27 review — 27 August 2026

**Scope.** Continuation of the authorization audit sprint 26 started. Both
findings correct. The first is student impersonation and is worse than anything
found before it.

---

## Finding 1 — the class code protected nothing

`findClassByCode` validated the code and then **threw it away**. Nothing
recorded that a browser had proved anything.

- `/join/[classId]` took a class id and rendered the class name, the teacher's
  name, the grade, and **every child's display name and avatar**. No proof that
  the caller had ever seen that class's code.
- `chooseStudent(studentId)` took any student id in the database and wrote that
  child's session. It did not check a grant. It did not check that the student
  was even in the class whose roster had just been shown.

So the only credential the privacy page claims — *"A class code protects a
child's own progress list"* — protected neither the roster nor the account. A
direct URL listed a school's children by name; a direct action call logged in as
any of them. Demo ids are public and predictable; random ids in production would
have hidden the missing rule rather than supplied one.

### The fix

Entering the correct code now writes a **signed, expiring, class-bound grant**,
reusing the HMAC the session cookie already uses. Ten minutes, `httpOnly`, its
own cookie:

```
{ kind: "join", classId, exp }
```

`/join/[classId]` refuses unless the grant names **that exact class** and
redirects to `/join` otherwise. `chooseStudent` verifies the grant itself rather
than trusting the page that rendered the buttons: grant present, student exists,
`student.class_id === grant.classId`, class not archived. Then it **spends the
grant** before writing the session. Archived classes no longer hand out grants
at all.

The comment on the token says why it exists, because the next person to read it
should not have to reconstruct the hole from a diff.

## Finding 2 — the windows were UI, not rules

Two halves.

**Missions.** `/student/play/[slug]` accepted any shipped mission, and
`beginMission`, `submitDecision`, `finishMission` and `replayMission` accepted
any slug. The student home renders only assigned missions, and that was the
whole of the enforcement — so a child could open an unassigned mission by URL
and record real evidence into it.

**Check-ins, and this is the worse half.** `nextBenchmarkFor` offered the spring
form *the moment the fall form was completed*. There was no window state and no
date anywhere in the product. The page and both actions accepted either form at
any time. Meanwhile the administrator pages, the plans page and the school
report all called them **fall and spring windows** — so a child could take both
back to back and the report would present the difference as a year's change.

Sprint 24 already narrowed the claim from "growth" to "the difference between
two authored check-ins". This is the other half of the same honesty problem: the
time separation the product's whole annual framing rests on did not exist.

### The fix

Both are rules now, in `src/lib/domain/eligibility.ts`, pure and shared by the
page loader and the server action:

- `missionAccessFor` → `assigned` when the class has it, `replay` when the child
  already completed it, `denied` otherwise. **Replay is a documented exception**:
  the home page links "Play again", replays are write-free, and withdrawing an
  assignment should not delete a child's access to work they already did.
- `canTakeBenchmark` → open only when the school's window names that form, and
  only when that form is not already finished. A completed form cannot be
  reopened while its window is still open.

**The window is real state now.** `schools.benchmark_window` is `closed | pre |
post`, defaulting to closed, with an administrator control on the programme page
and an audit entry when it changes. The note beside it says the thing worth
saying: *"a window opens because somebody opened it, and closes the same way."*
The seeded demo is `closed`, which is correct — both its windows have run.

`nextBenchmarkFor` moved out of `benchmark.ts` and takes the window. The old
one is deleted rather than deprecated, with a comment where it was, so nothing
can import the window-blind version by accident.

## Tests

Fifteen. The grant is asserted at the token layer where the session tamper cases
already live:

- Round-trips; refuses a different key; **refuses a grant whose class was
  swapped after signing** (a grant for A must not become a grant for B);
  expires at the boundary in both directions; refuses a session token presented
  as a grant and the reverse; refuses malformed input.

The eligibility rules are asserted directly, including the one that was the
whole defect:

- **`canTakeBenchmark({ window: "pre", form: "post" })` is false**, and
  `nextBenchmarkFor(finishedPre, "pre")` is null. Finishing fall does not open
  spring.
- A finished form cannot be reopened while its window is open.
- Both forms shut while the school is `closed`.
- An unassigned mission is `denied`; a completed one is `replay` even with the
  assignment withdrawn.

And wiring assertions, because a rule existing is not every path using it: both
join surfaces must read the grant, `chooseStudent` must check `class_id` and
spend the grant, both student pages must call the rules, and **each of the six
student actions must go through `requirePlayableMission` or
`requireOpenCheckIn`**.

**381 tests, up from 364.**

### Verified in the running app

`/join/cls_room12` with no grant redirects to `/join`. Entering MAPLE-317 opens
the roster. Holding that grant, `/join/cls_room4` redirects to `/join`. As the
demo student, `/student/checkin/post` and an unassigned mission URL both
redirect to `/student`.

## What this says about the review process

Sprint 26 found that a class belongs to its teacher and I wrote that the rest of
the route surface was unaudited. It was, and the student side was worse than the
staff side: staff could see one class they should not, and anyone at all could
become any child.

The shape is identical in both sprints and worth naming once more. **Every
authorization check in this product was a check that a record existed.** Does
this class exist, is it in my school, is this student a real student, is this a
shipped mission, is this a real form. Not one asked whether the person asking
was entitled to it. That reads as authorization until somebody types a URL.

The second finding adds something new: **the product's commercial framing was
load-bearing on state that did not exist.** "Fall and spring windows" is not
decoration — it is what makes an annual subscription and an annual report
coherent — and there was no field, no date and no rule anywhere behind it. That
is the same class of defect as sprint 25's "certified": a word doing work the
system could not support. Sprint 25 fixed it by changing the word. Here the word
was worth keeping, so the state got built.

## Deliberately left

- **`enterDemo("student")` still writes a student session directly**, bypassing
  the grant. It is an explicit demo button on the sign-in page, not a route a
  child reaches, and it is the mechanism the whole demo rests on. Worth knowing
  it is there.
- **No route audit is complete.** Two sprints have each found what they were
  pointed at. Nobody has enumerated every route and asked who may reach it.
- Sprint 24's instrument limits still stand: the forms are unequated and carry
  one item per skill. Real windows make the time separation true; they do not
  make the forms parallel.
