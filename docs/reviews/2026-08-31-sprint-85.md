# Sprint 85 — the repository sold two different products

**Date:** 2026-08-31
**Reviewed against:** HEAD `af18893`
**Scope:** buyer-facing scope claims, plus one derived source of truth and one
test file. **Includes the acceptance correction** that made the scope a product
invariant rather than a sales sentence, and which exposed a schema/form
contradiction reported below rather than resolved. No curriculum change, no evidence change, no grade support removed, no
schema, no field. This is a contract correction, not a program change.

## The finding, verified before changing anything

The content model is unambiguous, and I checked it rather than taking the
finding on trust:

| Fact | Evidence |
| --- | --- |
| All 27 core missions are grades 2–4 | `grep -o 'gradeBand: "[^"]*"' src/content/missions/*.ts` → **27 × `"2-4"`, nothing else** |
| First Look is two tracks of three | `src/content/foundations/*.ts` → 3 × `"1-2"`, 3 × `"3-5"` |
| A class runs one track | `foundationsForGrade` → `trackForGrade(grade)`, one track, and the module comment says so outright |
| First Look records no skill evidence | `segment: "foundation"`, enforced in `validateMission` |
| The assessed spine keys off the core missions | check-ins, nine-skill evidence, badges and the school report all read `attempt.evidence` from those missions |

So the assessed product is **grades 2 to 4**. A grade 1 or grade 5 class gets
three introductory sessions that deliberately move no competency figure.

Some surfaces said that correctly — the For your school card ("Grades 2 to 4"),
the `CreateClassForm` hint, the curriculum footnote. Six did not:

| Surface | What it said |
| --- | --- |
| `README.md` opening | "gives students in **grades 1–5** rehearsed practice…" |
| `src/app/layout.tsx` root metadata | "…teacher-guided scenarios for **grades 1 to 5**" |
| `SiteFooter` | "An annual subscription… gives **grades 1 to 5** rehearsed decisions" |
| `/approach` metadata | "why **grades 1 to 5** rehearse AI decisions **in authored story missions**" |
| `/curriculum` metadata | "Six First Look sessions for **grades 1 to 5**, then twenty-seven…" |
| `/plans` Single classroom | "**All 27 missions and both check-in forms**" — no grade qualifier at all |

The Approach line is the worst of them: it attaches grades 1 to 5 to *the story
missions*, which is the assessed thing. The Curriculum line does two wrongs at
once — the range, and "six sessions" for a class that receives three.

**The commercial consequence.** A grade 1 or grade 5 buyer reads an annual
subscription for their students, prices it, buys it, and then finds every library
card in the product saying grades 2 to 4 and their own track carrying no
evidence. That is a failed setup in front of a class, a trust problem with the
teacher who has to explain it, and a straightforward pilot or renewal objection
for a district: the public scope conflicts with the product's own content model.

## The correction

### A derived source of truth, not a phrase list

`src/content/scope.ts` computes the scope from the content:

```ts
CORE_GRADE_BAND            // "2-4"  — from MISSIONS, throws if they ever disagree
CORE_GRADE_LABEL           // "grades 2 to 4"
CORE_MISSION_COUNT         // 27
FIRST_LOOK_TOTAL_SESSIONS  // 6
FIRST_LOOK_SESSIONS_PER_CLASS  // 3 — throws if the tracks are ever uneven
FIRST_LOOK_TRACK_LABELS    // ["grades 1 and 2", "grades 3 to 5"]
```

Both derivations **fail closed with a named cause** rather than picking a value.
A curriculum spanning two bands is not a scope describable in a sentence, and
uneven tracks make "a class receives three" unsayable — in both cases the honest
failure is a build that stops rather than marketing copy that quietly narrows.
The footer and the Plans page consume these values directly, so the content model
and the price list cannot drift apart.

### What each surface now says

- **README** — "students in **grades 2–4**", then First Look described as six
  sessions in two tracks "of which a class runs the three written for its grade",
  ending "A grade 1 or grade 5 class can be created and taught First Look, and
  that is what it gets; First Look records no skill evidence by design."
- **Root metadata / Approach metadata / Curriculum metadata** — the missions
  carry the band; First Look is named as an introduction with per-class counts.
- **Footer** — interpolates `CORE_GRADE_LABEL`, then names both tracks.
- **Curriculum hero** — retitled "Twenty-seven missions for grades 2 to 4, and an
  introduction before them", and the First Look section lede changed from "Six
  sessions for a class" to "Six authored sessions in two tracks, so a class runs
  the three written for its grade".
- **Plans** — the bullet is now `All 27 core missions and both check-in forms,
  written for grades 2 to 4`, with a second bullet for First Look naming six,
  three-per-class and both tracks. A new section, **"What a subscription is for,
  and which grades"**, says the assessed program is grades 2 to 4, that First Look
  is included and *is not part of that*, that it records no skill evidence, and —
  plainly — "a grade 1 or grade 5 class can be created and taught First Look, and
  that is what it gets: three sessions, not a year of assessed practice. If you
  are buying for those grades, buy it for that."

Nothing was removed: grade 1 and 5 classes, First Look, and every curriculum
detail are untouched.

### One thing the browser found that the source sweep did not

`/approach` still rendered "grades 1 to 5" after every file above was corrected.
The educator orientation's first module was titled *"What grades 1 to 5 actually
need"*, and that title renders in the module list **on a buyer page**, beside the
plan copy. True of the age band the product touches, and exactly the reading this
sprint exists to remove. Retitled to "What 6 to 11 year olds actually need",
which is the body's own opening sentence and carries no scope claim. A test now
asserts no orientation module title contains the range.

## Acceptance correction: the contract was not enforced by the product

The first pass wrote a truthful commercial scope and enforced it nowhere. Checked
rather than assumed:

- `src/app/teacher/missions/page.tsx` rendered the grade tag **only when
  `isFoundation`** — every core card was untagged, while the new Plans copy said
  "every mission card says its grade band on its face"
- it offered an `AssignToggle` for every class on every card
- the class page rendered all 27 core toggles regardless of `classroom.grade`
- `setAssignmentAction` validated the mission and the active class and **never
  the grade**
- `missionAccessFor` and `canTakeBenchmark` had never seen a grade at all

So a mismatch was assignable and playable, and children could be sent content
outside the reading band it was levelled for.

### One derived predicate

`classMayBeAssigned(grade, mission)` in `lib/domain/eligibility.ts`, keyed on the
mission's own `segment`/`track`/`gradeBand` and on `CORE_GRADE_BAND` — not on a
list of ids, so adding curriculum cannot widen it. A class may be given the First
Look track `trackForGrade` picks for it, and the core curriculum only if its
grade is inside the band.

**Assignment and play are bounded; preview is not.** A teacher can still open,
read and put any mission on the board. What is bounded is what reaches a child.

### Enforced at four layers

| Layer | Behaviour |
| --- | --- |
| `setAssignmentAction` | refuses `assigned: true` above the write, naming the mission's band and the class's grade. **`assigned: false` stays open** so a stale or legacy row can be removed rather than stranded |
| student map | lists only assigned **and** in-band missions |
| `/student/play/[slug]` and `beginMission`/`submitDecision` | `missionAccessFor` fails closed on an out-of-band mission, **including a completed one** — a write-free replay of an out-of-band session is the same reading-band problem in a quieter place |
| check-ins | `canTakeBenchmark` and `nextBenchmarkFor` return closed/none outside the core band, because the forms measure the nine skills the core missions teach |

Historical records are untouched throughout: an out-of-band row is hidden and
refused, never deleted, and staff records stay readable.

### Both teacher surfaces

The band now renders on **every** card and every row. An ineligible switch is
replaced by a stated `Grades 1-2 · unavailable for Grade 3`, so the server
refusal is a backstop rather than the workflow. Eligible behaviour is unchanged.

## The contradiction, found and then closed

Writing the enforcement tests surfaced something larger than the finding:

```
schema.ts:79   grade INTEGER NOT NULL CHECK (grade BETWEEN 2 AND 4)
teacher.ts     if (![1, 2, 3, 4, 5].includes(grade)) return { error: … }
CreateClassForm  <option value="1">Grade 1</option> … <option value="5">
```

An administrator choosing **Grade 1** or **Grade 5** did not get a message. The
Server Action **threw** — verified end to end as
`CHECK constraint failed: grade BETWEEN 2 AND 4`. Those classes could not be
created at all, and sprint 85's own copy claiming they could was false.

I first reported this as an open product decision. It is not: the product's niche
is authored decision practice for `CORE_GRADE_BAND`, the schema constraint is the
intended boundary, and offering grades the database refuses is a **setup defect**
that hands a database error to an administrator. Closed on the grades 2–4 side,
with **no migration and no curriculum change**:

- **`CreateClassForm`** offers exactly Grade 2, Grade 3 and Grade 4. The hint
  that promised "Grades 1 and 5 get the First Look sessions written for them" is
  replaced by what is actually true within the band: *"Grade 2 runs the early
  First Look track; grades 3 and 4 run the upper one."*
- **`createClassAction`** validates against `CREATABLE_GRADES` **before any
  repository call**, so a refusal writes nothing and reads as a sentence:
  *"Choose a grade from 2 to 4. The missions are written and reading-levelled for
  that band."*
- **`CREATABLE_GRADES` is derived** from `CORE_GRADE_BAND`, not typed, so the
  form, the action and the schema cannot drift from the band the curriculum
  declares.
- **The schema is untouched.**

First Look still ships two authored reading-level tracks, described truthfully:
the tracks exist because those are the two reading levels the sessions are
written for, and within this band a Grade 2 class runs the early one and Grades 3
and 4 the upper one. Nothing claims grade 1 or grade 5 class support.

### The optional guard was not a guard

`missionAccessFor`, `canTakeBenchmark` and `nextBenchmarkFor` took the new bound
as an **optional** parameter, so the invariant failed open for any caller that
forgot. All three are now **required**, which turns omission into a type error —
and it immediately found 24 call sites across four files, every one of which now
passes the grade explicitly. The two production callers that resolve a class
pass `?? 0`, so an unresolvable classroom closes the check-in rather than opening
it.

The test that preserved the unbounded behaviour is deleted. In its place, a
source assertion proves omission is impossible: no `grade?:`, no `eligible?:`,
and the guards read the value unconditionally with no "if supplied" escape.

## Third acceptance correction: the curriculum hero still offered an uncreatable class

The final boundary correction went through Plans, the README, the form and the
action, and missed the one buyer page nobody re-read. The curriculum hero still
ended:

> …a grades 1 and 2 track, or a grades 3 to 5 track — **which is also what a
> grade 1 or grade 5 class is offered.**

Written in the first pass, before the boundary was settled, and left behind when
it was. It is false: classes are created in `CORE_GRADE_BAND` only, the action
refuses 1 and 5 before any repository write, and the schema allows only 2 to 4.
A buyer reading the curriculum page could still take it as permission to buy for
those grades and have their administrator fail at setup — the exact contradiction
this sprint existed to close, surviving on the page that describes the curriculum.

The hero now distinguishes **reading level** from **creatable class grade**,
which is the distinction the whole thing turns on:

> Before any of it, First Look gives a class that has never been told what AI is
> three short sessions. It ships two reading levels — a grades 1 and 2 track and
> a grades 3 to 5 track — and within this program a Grade 2 class runs the early
> one while Grades 3 and 4 run the upper one.

A comment in `tests/program-scope.test.ts` calling grade 1 and grade 5 "real,
supported" is corrected to say what is actually true: those phrases name two
authored reading levels and stay; a **class** in those grades does not exist.

### The sweep

Every remaining `grades 1`/`grades 3 to 5` mention on a buyer surface — the
curriculum metadata, the root metadata, the footer, the README — was read. All
name a **track**, none claims a class, and all are left alone. The two remaining
"Grade 1 and Grade 5" strings in tests are historical narration describing what
the form used to offer, which is accurate.

## Known gaps

- **The regex half is still a regex.** The derivation is structural; "no surface
  attaches 1–5 to what is sold" is a pattern over seven files. A surface added
  tomorrow is not in the list, and a phrasing outside the 80-character window
  would pass. Enumerating `src/app/(site)/**` would close the first half of that.
- **Nothing renders the scope sentence.** `PROGRAM_SCOPE_SENTENCE` is derived,
  asserted and used by no page — the surfaces interpolate the parts instead,
  which reads better and means the composed sentence is currently dead weight.
- **The 27-mission count is asserted in prose in several places** ("twenty-seven"
  as a word). Only Plans interpolates `CORE_MISSION_COUNT`; the README and the
  hero spell it out, so a curriculum that grew would leave them stale without
  failing anything.
- **The class page's unavailable state is unreachable in a browser.** Every
  creatable grade is in the core band and the page already scopes First Look to
  one track, so that branch is defense in depth covered by tests only. It is
  reachable through `setAssignmentAction` from a stale tab, which is what it is
  for.
- **`?? 0` is a sentinel.** The two production callers that may not resolve a
  classroom pass grade `0`, which is outside every band and therefore fails
  closed — but it is a magic number standing in for "no class", and a caller
  reading it could reasonably wonder. A resolved-class type would say it
  properly.
- **The sweep that missed this one was a grep over named files.** The curriculum
  hero survived three corrections because each swept the surfaces the finding
  named. Enumerating `src/app/(site)/**` would have caught it; the new guard now
  runs over the buyer-surface list, which is still a list.
- **The band is enforced at assignment and play, not at the roster.** Nothing
  stops a school putting an eight-year-old on a Grade 4 roster; the product takes
  the class's grade as given. That is the right boundary for a product that does
  not collect ages, and it is worth stating rather than assuming.
