# Sprint 69 — archiving was bookkeeping, not a boundary

**Date:** 2026-08-29
**Reviewed against:** HEAD `6ae0159`
**Scope:** make `archived_at` an authorization boundary and revoke the class
credential on the transition. No student field, no free text, no telemetry, no
risk scoring, no new auth system, no schema change.

## The defect

Archiving dropped a cohort out of the active licensed-seat count and refused new
code entry at both `/join` steps. It did nothing to a student session already
issued.

`currentStudent` loaded the student, loaded the class, compared the session's
bound code — sprint 68's fix — and handed back an **archived** classroom. Every
student page and every instructional action trusts that resolver, so a child
with a live twelve-hour cookie kept the roster-linked experience and kept
opening and recording authored mission and check-in work after the class was
"finished". Both archive paths were affected: `archiveClassAction` and
`rolloverYearAction`, which archives the whole outgoing year.

Commercially that is a school archiving a cohort to free licensed seats while
already-signed-in devices carry on using the instructional product.
Operationally, "finished class" and year rollover did not close student access.

## The correction

**One line in the resolver, one transaction in the repository.**

`currentStudent` refuses an archived class — closing every student page and
mutation on the next request, since they all go through it.

That alone leaves a second hole: restore the class inside those twelve hours and
every pre-archive session revives, because the code it is bound to is the code
the class still has. So `archiveClass` issues a **new join code in the same
transaction** as the archive:

```ts
if (current && !current.archived_at) {
  db.prepare("UPDATE classes SET archived_at = ?, join_code = ? WHERE id = ?")
    .run(nowIso(), generateJoinCode(db), id);
}
```

No schema field — the existing credential lifecycle does the revocation, exactly
as code rotation already does. Sessions and grants are bound to the old code and
stay invalid **across a restore**; everyone rejoins with the code the class has
now.

- **Both paths covered**, because both go through this one function. The manual
  archive and the rollover are not two implementations.
- **Idempotent.** Archiving an already-archived class touches nothing: no second
  code, no moved timestamp. The read and the write share one `BEGIN IMMEDIATE`
  so two archives arriving together cannot both see an active class and both
  rotate.
- **Unknown class is a no-op**, as before.
- **Staff sessions unaffected** — a teacher must still be able to restore,
  rename or delete an archived class.
- **Restore's seat cap and the subscription rules are untouched.**

### Browser

**A single browser profile holds one `airk_session` cookie**, so the student and
administrator sessions cannot be live in it at the same time. The two halves were
therefore driven as separate passes, and are recorded separately. Both halves
were run at **both** widths.

**Student device — 1280×800, then 768×1024.** Joined with the current code, chose
a child, `/student` rendered their name, missions and badge strip. The class was
then archived through the same `archiveClass` transaction the administrator
action performs. Navigating to `/student`:

```
url /join   serverError false   stale.name false
            overflow    false   stale.missions false
            go.unobscured true  stale.badges false
```

The class was then **restored** with the old cookie still in the browser:
`/student` still landed on `/join` — `reactivated: false` — proving a restore
does not revive a pre-archive session. Typing the **old** code was refused
(*"That code did not match a class"*), and typing the **new** code returned the
child to `/join/cls_room12`.

**Administrator — 768×1024, then 1280×800.** The real UI throughout. Signed in
as the administrator, opened `/admin/classes`, pressed **Archive** on Room 12

corrected confirmation in full, pressed **Archive class**. The row became
`Room 12 Archived` and the code changed — `COMET-UMBRELLA-604` on the tablet
pass, `COMET-JACKET-540` on the desktop pass — with no server error and no
document overflow (the wide table scrolls inside its own `overflow-x: auto`

## Remaining gaps

- **Containment is per request.** A page already rendered on a child's screen
  stays rendered until they navigate. Nothing pushes to a connected browser, and
  the copy says so rather than implying otherwise.
- **Revocation is code rotation, not session invalidation.** There is no session
  store to revoke against, so "invalidate this child's session" is only
  expressible as "change the credential it was bound to". That is enough for
  archive and rotation; it could not express, say, signing out one child while
  the class carries on.
- **The seat-count consequence is now real but still coarse.** Archiving frees
  seats *and* closes access together. A school wanting one without the other has
  no way to ask for it, which is the right default and worth naming.
- **A restore always costs a rejoin.** Archiving by mistake and restoring
  immediately still sends every child back to the join screen with a new code.
  That is the price of not letting a restore revive sessions, and the
  confirmation now says so before the administrator commits.
