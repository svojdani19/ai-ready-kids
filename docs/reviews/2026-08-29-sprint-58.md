# Sprint 58 — "soon" was a subscription that never ended

**Date:** 2026-08-29
**Scope:** contract-date validation and a third subscription state. No schema,
no billing, no scope beyond making unreadable dates safe.

## The finding

`term_starts_on` and `term_renews_on` are unconstrained text, and sprint 49's
`subscriptionState` compared the renewal **string** lexicographically without
ever asking whether it was a date.

`"soon"` sorts after every `YYYY-MM-DD`, so a school with that value stayed
**active indefinitely** — a paid term that could never end. `"2026-13-45"` and
`"2026-02-30"` were treated as ordinary deadlines. A timestamp or a padded
string compared as text. Program rendered `Invalid Date` and `in NaN days`,
Overview silently dropped its renewal warning because `NaN <= 60` is false, and
the annual JSON exported the raw values to a district office.

## The rule, and the one I got half right

Sprint 49 reasoned that an unset renewal date cannot lapse a school, because
refusing to teach over a blank field would be the software inventing a
commercial fact. **That is true and it was half an answer: active is also a
commercial decision.** A paid product that cannot verify its own term should say
so rather than quietly pick the reading that keeps teaching.

So there are three states now, and `needs-configuration` is **neither active nor
lapsed**. Nothing ended; the record is unreadable. It must never be labelled
ended or overdue, because telling a school its subscription expired when the
truth is that a field says `"soon"` is a different — and wrong — commercial
claim.

## The validator

Exactly `YYYY-MM-DD`, and a real day, checked by UTC round-trip:

```ts
const parsed = new Date(`${value}T00:00:00.000Z`);
return !Number.isNaN(parsed.getTime()) && parsed.toISOString().slice(0, 10) === value;
```

The round-trip is what rejects an impossible day: `2026-02-30` parses to March
2nd, which does not stringify back. **A real leap day survives** — `2024-02-29`
and `2000-02-29` round-trip exactly, `2023-02-29` and `2026-02-29` do not. The
pair is also ordered: a term cannot renew before it starts, though equal dates
are allowed since a one-day term is odd rather than unreadable.

Non-coercive throughout — no `trim`, no `Date.parse`, no normalising a nearly
right value into a right one. Asserted by a test that strips comments first,
having learned that lesson three times.

## Failing closed, and who hears what

`assertSubscriptionActive` throws `TermNotConfiguredError`, distinct from
`SubscriptionLapsedError`. `lapsedRefusal` returns the matching message, and
`asExpectedError` converts both — so no gated action can turn a configuration
refusal into an error page.

Every gate reads from one place. `schoolHasLapsed` — the name the child-facing
surfaces use — is now `schoolInstructionClosed(...) !== null`, so **both reasons
close the same doors for a child** and they see only *"Your class isn't open
right now. Ask your teacher."* A test asserts the four child surfaces mention no
configuration or billing detail at all.

Staff get the distinction:

> This school's subscription dates cannot be read, so classroom changes are
> paused… **This is not an expiry** — nothing has ended and nothing has been
> deleted. Records, reports and exports are all still available. Ask your
> account contact to correct the subscription dates on the account.

Everything non-instructional stays open, exactly as sprint 49 established:
reports, exports, staff administration, deletion, retention controls, the quote
request and sign-out.

## Buyer surfaces and the export

The day count is **not computed** for an unreadable term, which is what produced
`Invalid Date` and `in NaN days`. Program shows *"Term started: Needs
configuration"* and *"Subscription dates: Need configuration — Classroom changes
are paused"*; Overview carries its own note. No raw value, no invented renewal
status.

`termStartsOn` and `termRenewsOn` are **removed from `SchoolReport` entirely**.
They had one consumer, inside a block that only renders for a verifiable term,
which now reads the school directly. This is sprint 57's finding applied to the
same shape one field over: account metadata does not belong in a report about
demonstrated competencies, and the JSON serialises whatever the object holds.

## Tests

Eleven new cases, **all failing against the previous code** when stashed.
Malformed sweep: `""`, `" "`, `"soon"`, `"2026-13-45"`, `"2026-02-30"`,
`"2026-9-1"`, leading and trailing whitespace, a timestamp, `"26-09-01"`,
`"2026/09/01"`, plus `null`, `undefined`, a number, `{}` and `[]`. Leap days both
ways. Start-after-renewal. A whole-database snapshot proving a refusal writes
nothing at all. Recovery restoring normal active **and** lapsed behaviour. The
child surfaces carrying no configuration detail. Gate consumers pinned. Buyer
pages free of raw dates, `Invalid Date` and `NaN`. The export clean and the CSV
unchanged. And the quote request neither gated nor rewriting the dates.

**635 tests, up from 622.**

## Verified in the browser

With `term_renews_on = 'soon'`, at **1280×800** and **768×1024**:

- **Staff shell**: *"Subscription dates need configuration… This is not an
  expiry — nothing has ended and nothing has been deleted."*
- **Overview**: the configuration note and *"Classroom changes are paused"*.
- **Program**: *"TERM STARTED | Needs configuration"* and *"SUBSCRIPTION DATES |
  Need configuration | Classroom changes are paused"*. **No `Invalid Date`, no
  `NaN`, no `soon`** on either page, no overflow.
- **A refused write**: rotating a class code returned the configuration refusal,
  not an error page; the code was **unchanged** in the database and no class or
  student row moved.
- **The child**: a correct class code returned *"Your class isn't open right now.
  Ask your teacher."* with **no** mention of subscription, configuration,
  renewal, dates or an account contact.
- **The JSON export's `school` block**: name, district, city, state, schoolYear,
  retention — and **no `termStartsOn`, no `termRenewsOn`, no `soon`**. CSV clean.
- **Recovery**: restoring `2026-09-01` immediately returned *"TERM STARTED |
  August 18, 2025"*, *"RENEWS | September 1, 2026 | in 3 days"*, and the staff
  notice disappeared.

Demo restored: plan school, 120 seats, retention 12, term 2025-08-18 →
2026-09-01, four classes, 90 students, 885 attempts, 16 audit rows.

## Observed, not built

- **The columns are still unconstrained.** Safe, visible and recoverable; not
  prevented. A CHECK constraint needs a migration.
- **`year_starts_on` and `year_ends_on` are a different question.** They drive
  retention, which already blocks on an empty year-end and on an unrecognised
  window — but a *malformed* year-end (`"2026-13-45"`) would reach `addMonths`
  and produce an Invalid Date rather than a refusal. That is the next one.

## The lesson

**A string comparison is not a date comparison, and lexicographic order is a
trap that flatters the wrong value.** `"soon" > "2026-09-01"` is true, which
happens to mean "not yet due" — the one answer that keeps a school teaching for
free forever. Had the malformed value sorted the other way it would have lapsed
every school instantly and been found in a day.

The deeper one is about sprint 49's reasoning, which I still think was right as
far as it went: *refusing to act on missing data* was correctly identified as a
decision, and *continuing to act on it* was not. When a rule says "we will not
invent X", check whether the fallback invents not-X.
