# Sprint 74 — one number that moves every deletion date, committed apart from its record

**Date:** 2026-08-29
**Reviewed against:** HEAD `bd8e9ea`
**Scope:** `setRetentionAction` only, plus one narrow guard entry. No sweep of
the remaining configuration actions. No schema change, no student-data field.

## The finding

`setRetentionAction` wrote `schools.retention_months` and inserted
`retention.updated` afterwards, as two commits. Unlike a profile setting, this
one field moves the scheduled deletion date for **every cohort** and changes
which children's records the purge considers eligible.

A failing audit insert therefore left a new deletion schedule running with no
trustworthy record of who set it or when — while the administrator might see an
error page — on the same page that promises *"Every configuration and deletion
action, with who did it and when."*

## The correction

Option validation stays **above** the transaction, so a rejected option never
takes a write lock. `setRetentionMonths` and the `retention.updated` audit are
wrapped in `auditedWrite`: both commit or neither does. On failure the action
returns a calm inline error, never an error page:

> The retention window was not changed. Every class keeps the same retention
> status and the same scheduled deletion date it had before you pressed Save,
> and no records were deleted. Try again.

It names the two things an administrator would otherwise go and check — the
schedule did not move, and nothing was deleted while the save was failing — and
it does **not** claim the attempt was recorded, because the rollback takes the
audit row with it. No support promise; a test forbids `account contact`,
`support`, a response time, and any claim of being logged or audited.

### The guard, extended by exactly one entry

`setRetentionMonths(` joins the consequential-write list. It is not destructive
in itself, which is the point: it is the one configuration write whose loss is a
data-governance problem rather than a cosmetic one, because it reschedules
deletion for every cohort. The other configuration writes stay out deliberately
— keying the guard on "any write at all" would turn it back into the action-name
list it replaced in sprint 73. The non-empty proof now expects nine wrapped
actions including `setRetentionAction`.

## Proof

`tests/retention-atomicity.test.ts` drives the **exported action** with a real
admin session, a real database and real `FormData`, against a fixture that also
contains **a second school** on 24 months.

Snapshots compare, as strings: the complete school row, the other school's row,
every class row, students, attempts, benchmarks, audit rows, **derived
`retentionRows`** at two fixed dates, and **the exact set of purge-eligible
class ids** at those dates. Eligibility is measured at fixed boundaries
(2026-09-11, 2026-09-13, 2027-06-11) rather than "now", so it is a fact rather
than a function of when the suite runs.

**Audit failure:** `BEFORE INSERT ON audit_log WHEN NEW.action =
'retention.updated' RAISE(ABORT)`. The action returns `RETENTION_FAILED`, and
every snapshot is exact — school row, class rows, derived due dates, purge
eligibility, audit rows, other school.

**Retry:** the school row differs in `retention_months` **and nothing else**;
every class row is byte-identical, because the policy is not copied onto them;
each due date moves by exactly **−9 months** from that class's own recorded
year-end, keeping the same day of month; eligibility at 2026-09-11 is empty and
at 2026-09-13 is all four classes; student, attempt and check-in counts are
unchanged; exactly **one** new `retention.updated` audit carrying the policy the
screen reported; and the other school is still on 24 months.

**Invalid option:** `7`, `0`, `-12`, `"twelve"` and `""` each return the existing
validation error and the full snapshot is exact.

> One fixture bug worth recording: the derived-row helper first used
> `getPrimarySchool`, which is `ORDER BY created_at LIMIT 1` — and my second
> school was created earlier, so the test was measuring the wrong school's
> policy and reporting a 0-month move. Reading by id fixed it. A test that adds
> a second school must not then ask for "the first one".

## Known gaps

- **Eleven configuration actions still audit outside a transaction**:
  `updateSchoolAction`, `requestPlanChangeAction`, `setBenchmarkWindowAction`,
  `addTeacherAction`, `reassignClassAction`, `createClassAction`,
  `addStudentAction`, `renameStudentAction`, `setAssignmentAction`,
  `completeCertificationAction`. Each is a single-row write whose loss cannot
  leave a half-finished state. Retention was pulled out of that set because it
  reschedules deletion for every cohort; the rest genuinely are cosmetic or
  additive by comparison. Whether that line is in the right place is the
  question worth putting to a reviewer.
- **`setBenchmarkWindowAction` is the closest call.** It decides which check-in
  children are offered, so a lost record of who opened a window is a real
  governance question — just not one that moves a deletion date. It was left out
  to keep this sprint to the stated scope.
- **Failures still write nothing**, consistent with sprints 70–73.
- **The guard reads source text** and would miss a write reached through an
  alias or a helper.
