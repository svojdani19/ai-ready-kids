# Sprint 35 — the help note that told an administrator to delete a class

**Date:** 2026-08-27
**Scope:** one P1 finding. A stale instruction on the admin Classes page, and
the missing capability that would have made it unnecessary.

## The finding

`src/app/admin/classes/page.tsx` told administrators:

> Codes are per class and can be regenerated by deleting and recreating a class.

That was false. Sprint 30 gave the teacher of record a **New code** control on
their own class page, which rotates the code, invalidates outstanding join
grants immediately, and keeps everything else. `README` already documented it
correctly. The admin page had simply never been updated.

The sentence was not merely out of date. It sat on the same page as **Delete
data**, whose confirmation is explicit about what it removes: the roster, every
mission attempt, the skill evidence, the badges and both check-ins. So the
product's own written instruction, given to the one role that has the delete
button, was to destroy children's records in order to perform a routine
security task that the product already knew how to perform without touching
them.

The routine part matters. A class code for seven- to ten-year-olds is projected
on a whiteboard, written on a slip that goes home, and read aloud across a
room. Needing a new one is not an incident, it is a Tuesday. A product whose
answer to a Tuesday is "delete the class" has a data-loss defect, whatever the
delete button's own confirmation says.

## What changed

**Administrators can now rotate a code from the Classes page.** This was the
preferred resolution in the finding and it is the right one: the page already
displays the code, and a class credential is class configuration rather than a
child's record. It sits inside the administrator role exactly as sprint 26 drew
it — `canAdministerClass` covers "everything about the class as an object, and
nothing about the children in it".

- `rotateJoinCodeAsAdminAction` in `src/app/actions/admin.ts`. It reuses the
  same `rotateJoinCode` repository function the teacher control uses, so the
  same cryptographic generator and the same grant-invalidating behaviour, and
  scopes through the existing `ownClass` guard.
- `ownClass` now delegates to `canAdministerClass` rather than repeating the
  school comparison inline. The rule was already written down once; there is no
  reason for a second copy of it to exist and drift.
- The control sits **in the Code column**, beside the code it replaces, because
  that cell is where the new code appears and handing it out is the
  administrator's next action. Verified live: the cell updates in place.
- Its confirmation says what stops and what does not, in that order:

  > Give Room 12 a new code? The old one and anybody halfway through joining
  > with it stop working straight away. The class, its teacher, the roster,
  > assignments, mission history, badges and both check-ins are not touched.

  The second sentence exists because the control immediately to its right
  destroys every item it lists.
- The rotation is audited as `class.code_rotated`, naming the class and no
  child. A code changing is a fact about a class.
- The note at the bottom of the page is rewritten. It now says codes get read
  aloud and photographed, points at **New code**, notes the teacher of record
  can do the same, and states plainly that deleting a class is never the way to
  change its code.

**Every delete-and-recreate instruction is gone.** A repository-wide grep
returned exactly one, the sentence above; the other matches were this file's
own history and a code comment.

## Tests

Five, in `tests/access-control.test.ts` (461 total, up from 456).

- Rotation changes the join code **and nothing else**. The class row is
  compared field by field rather than spot-checked, and the roster, the
  assignments, every attempt row and every benchmark row are compared whole. A
  mission is played to completion first so "preserved" has something to
  preserve. Badges are derived from completed attempts rather than stored, so
  an intact attempt row is what keeps a child's badge.
- A grant issued against the old code is valid before the rotation and no
  longer matches the class's code after it.
- An administrator at another school is refused, and a teacher at this school
  is not made an administrator by this rule.
- The action goes through `ownClass`, records `class.code_rotated`, and reaches
  no roster; `ownClass` itself goes through `canAdministerClass`.
- The page no longer contains the delete-and-recreate advice, does contain the
  action, and its confirmation still says what survives.

## Verified live

Rotated Room 12 through the UI on the running dev server. Code changed from
`MAPLE-HERON-317` to `VELVET-OCTOPUS-101`; 23 students, 366 attempts, 43
benchmarks and 18 assignments all unchanged, and the other three classes
untouched. The audit row named the class and no child. The retired code was
then refused at `/join` with the ordinary "That code did not match a class",
and the new code reached Room 12's find-your-name page with all 23 names.

## Deliberately not changed

- **No curriculum, no student fields, no new administrator access to named
  rosters.** The Classes page still does not link to the teacher class page,
  and the sprint-26 test that enforces that still passes.
- The teacher's own **New code** control is untouched. Two roles can rotate a
  code; both go through the same repository function.
- `/join`'s placeholder is the literal string `MAPLE-HERON-317`, which is now a
  retired code in the demo data. It is a placeholder illustrating the shape of
  a code, not a claim about a live one, so it is left alone.

## Noted, not fixed

`src/app/(site)/privacy/page.tsx` has two unused-import lint warnings that
predate this sprint and are unrelated to it. Left for a sprint whose scope
includes that file.

## The lesson

**Adding a safe way to do something does not remove the old advice about doing
it the unsafe way.** Sprint 30 built the rotation and updated the README and
the teacher page. The one surface it did not update was the one where the
consequence of following the stale advice was worst, because that is the
surface with the delete button. Prose is not documentation of the code — it is
part of the product, and it is the part that goes stale without failing a test.
Both new checklist items come from this: re-read the instructions when the
capability changes, and never let a routine task be routed through a
destructive one.
