# Sprint 67 — a deletion right the code does not grant, and an assurance nothing enforced

**Date:** 2026-08-29
**Reviewed against:** HEAD `ab5d258`
**Scope:** deletion copy and the assignment write path. No account-deletion
feature, no new fields, no new views, no telemetry, no auth change, no
migration.

## 1. "A school can delete everything at any time"

`/privacy` said:

> A school can delete everything at any time without contacting us, because the
> data is theirs.

Every `DELETE FROM` in the repository, traced:

| Statement | File | Reachable from |
| --- | --- | --- |
| `DELETE FROM classes` | `repo/classroom.ts`, `domain/purge.ts` | Delete-now button, purge job |
| `DELETE FROM students` | `repo/classroom.ts` | Remove a student |
| `DELETE FROM attempts` | `repo/progress.ts` | Reset one attempt |
| `DELETE FROM assignments` | `repo/classroom.ts` | Unassign a mission |
| `DELETE FROM users` | `repo/school.ts` | `removeStaffAction` |
| `DELETE FROM <every table>` | `db/reset.ts` | **`scripts/reset-db.ts` only** |

Class deletion cascades to roster, assignments, attempts and check-ins through
the foreign keys. `removeStaffAction` refuses while the person owns any class
(archived ones included), refuses your own account, and refuses the last
administrator. Nothing anywhere deletes the `schools` row, the remaining
`users` and their `certifications`, `audit_log`, `meta`, or the account
settings. `resetDatabase` empties the tables and **re-seeds demo data** — it is
a developer script, not an erasure path, and no file under `src/app` references
it.

So there is no whole-school or account erasure, self-service or otherwise, and a
district relying on that sentence would have been relying on nothing.

### The correction

`DELETION_SCOPE` in `src/content/data-inventory.ts`, rendered on `/privacy` and
on `/admin/data`:

> Deleting a class removes its roster, every mission attempt, both check-ins and
> that class's own mission assignments, in one operation and immediately. Rows
> are removed rather than flagged, and there is no soft-delete table and no
> restore path. · An administrator can also remove a staff member once that
> person owns no classes. Nobody can remove their own account, and a school must
> keep at least one administrator, so the last one cannot be removed either. ·
> **Nothing in this build deletes the school record and its settings, the staff
> accounts that remain, their orientation answers, or the audit log. There is no
> whole-school or account erasure control in this demonstration — not
> self-service, and not by any other route the product offers.**

No support contact, ticket process, backup behaviour, compliance right or
timeline is invented in its place, and a test forbids each of those.

Aligned: `/for-schools` (*"Delete anything sooner at any time"* → *"You can
delete any class, and its records, sooner without waiting for the date"*), and
the README, which gains an explicit paragraph naming the self-service boundary,
the `reset-db` script's real nature, and the sentence that was wrong.

The audit-log line is now stated as a consequence rather than a feature:
deleting a class does not delete the record that it was deleted.

## 2. "Nothing here names a student"

The `assignments` inventory entry carried that assurance. `assignments.note` is
an unconstrained `TEXT` column, `assignMission` accepted
`note?: string | null` and wrote it, and the demo seed wrote *"Do this one
together on the rug before independent work."* into it. Nothing enforced the
promise — it held only because no form happened to call the parameter.

Traced end to end:

- **`note`** — written by `assignMission` (parameter) and by the seed. Its only
  caller, `setAssignmentAction`, never passed one. Rendered by nothing.
- **`due_on`** — hard-coded `NULL` in the `INSERT`, `NULL` in the seed, never
  written anywhere, rendered by nothing.

### The correction

The write surface is reduced rather than documented. `assignMission` has no
`note` parameter; the `INSERT` writes literal `NULL` for both columns and the
conflict clause is `DO NOTHING` instead of `DO UPDATE SET note = excluded.note`.
The demo seed writes no note. **No note UI was added.**

Both columns stay in the schema. Dropping them is a migration, and a migration
that erases values an existing database may hold is not something to do in
passing — so the inventory says so instead:

> Per class: which missions a teacher has opened and when. The table also has a
> due-date and a note column, **both unused**: nothing in the product writes them
> and no screen shows them.
>
> Assigned to a class, never to a child. No control in this product writes the
> note or the due date, so nothing new goes into them; **a database carried over
> from an older build may still hold a staff-typed note in that column.** A child
> cannot put text there or anywhere else — there is no free-text input in the
> student experience at all.

That keeps the two boundaries separate: child free text remains impossible
because there is no input path, while staff or legacy free text in a retained
column is a different and honestly-stated thing.

## Remaining deployment gaps, stated plainly

- **There is no account erasure.** A school that wanted its whole record
  removed would need someone with database access to do it. The product now says
  this rather than promising the opposite, but saying it is not fixing it.
- **The audit log is not deletable and outlives the records it describes.**
  That is defensible — it is what an audit log is for — but it means "delete the
  class" and "remove every trace of the class" are different operations, and
  only the first exists.
- **Two nullable legacy columns remain.** `assignments.note` and
  `assignments.due_on` are written by nothing now, but an older database may
  hold a staff-typed note in `note`. Removing them is a migration, deliberately
  not taken here.
- **`npm run reset-db` is destructive and unauthenticated at the shell.** It is
  a developer script and no route reaches it, which a test now enforces; it is
  still one command away for anyone with the filesystem.
