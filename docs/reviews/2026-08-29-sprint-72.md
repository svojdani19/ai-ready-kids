# Sprint 72 — repairing a school calendar was three commits, and one of them set retention dates

**Date:** 2026-08-29
**Reviewed against:** HEAD `f33dd64`
**Scope:** `setAcademicDates` and `setAcademicDatesAction`. No schema change, no
student-data field, no free text, no telemetry, no change to repair scope.

## The finding

`setAcademicDates` is a multi-write boundary that committed in pieces: the
school row, then the decisive read of the previous academic year, then a loop
repairing each candidate cohort's label and year-end. The action then wrote
`year.dates_set` separately after all of it.

A failure partway left the school calendar changed, **some** cohorts repaired
and others not, and no audit. That is not cosmetic: **each class's
`year_ends_on` is what its retention due date is calculated from**, so two
cohorts in the same year end up on different deletion schedules, one of them
still unschedulable — and nothing records that a save was attempted. A buyer can
trust neither the retention schedule nor the audit history afterwards.

## The correction

**`setAcademicDates` is now transaction-aware itself**, so direct repository
callers are safe too. `BEGIN IMMEDIATE` is taken **before** the read of the
previous academic year, because that read decides which labels are repair
candidates — locking afterwards would leave a window in which the answer could
change. An outer transaction is participated in and never committed or rolled
back here.

**The action wraps `setAcademicDates` plus the `year.dates_set` audit in
`auditedWrite`**, so the calendar write, every cohort repair and the success
audit commit together or nothing persists. Validation stays **before** the
transaction, so a rejected form never takes a write lock.

On failure the action returns a calm inline error, never an error page:

> The academic dates were not saved. The school year, its first and last day,
> every class year label and every class year-end date used to work out when
> records are deleted are all exactly as they were before you pressed Save. Try
> again.

No support-response promise — sprint 70's rule, and a test forbids `account
contact`, `support` and a response time in it.

The repair summary moved into `academicRepairSummary`, shared by the audit
detail and the on-screen message so the record and what the administrator was
told cannot drift apart.

## Failing-before

`tests/academic-atomicity.test.ts` builds a school whose calendar is unreadable
(`2025-2027` / `''` / `2026-13-45`) with **two genuine repair candidates** and
three controls:

| Row | Role |
| --- | --- |
| `cls_broken_a` | candidate — broken label, empty date |
| `cls_broken_b` | candidate — broken label, `2026-13-45` |
| `cls_valid_same` | control — same broken label, **valid** date `2026-06-30` |
| `cls_history` | control — real historical year `2024-2025` |
| `cls_other_school` | control — a different school entirely |

**A trigger with a counter aborts the second class update**, so the failure
lands strictly between two intended repairs. Against the un-transacted helper,
the probe shows exactly the defect:

```
school = 2026-2027 / 2027-06-12      ← calendar already moved
a      = 2026-2027 / (empty)         ← relabelled, retention date still unusable
b      = 2025-2027 / 2026-13-45      ← not repaired at all
audits = 0
```

One cohort half-repaired, one untouched, the school moved on, nothing recorded.
The corrected helper throws and the **entire snapshot is byte-for-byte
unchanged** — including the trigger's own counter row, which is how we know the
repair was inside the transaction rather than committed around it.

Against the un-transacted helper the atomicity test fails:

```
× rolls back the school write and the first repair when a later one fails
```

**Through the real action**, `BEFORE INSERT ON audit_log WHEN NEW.action =
'year.dates_set' RAISE(ABORT)` with a real admin session, real database and real
`FormData`: the action returns `ACADEMIC_DATES_FAILED`, the full school / class /
audit snapshot is exact, and `year.dates_set` rows are **0**.

**Retry with the trigger removed** asserts the exact new school dates; both
candidates repaired in label *and* year-end; `cls_valid_same` still on
`2026-06-30`; `cls_history` and `cls_other_school` and the other school's row
byte-identical; subscription dates and `retention_months` unchanged; the
repair-count message carrying both facts separately; and **exactly one**
`year.dates_set` audit whose detail carries the same two facts.

An outer-transaction participation test completes the set.

## Known gaps

- **Failures still write nothing.** A rolled-back save leaves no trace, so an
  administrator who retries successfully sees one clean audit entry and no sign
  the first attempt failed. Consistent with sprints 70 and 71, and still a gap in
  the history an auditor could read.
- **The other configuration actions are unchanged.** `setRetentionAction`,
  `setSchoolAction`, `setBenchmarkWindowAction` and staff removal still audit
  outside a transaction. Each is a single-row write, so a lost entry cannot
  produce a half-repaired state the way this one could — but the promise on the
  page covers them too.
- **`auditedWrite` is applied action by action.** Nothing structurally prevents
  the next configuration action from auditing separately; the guard names the
  actions that exist today.
- **The repair scope is unchanged and still narrow by design.** A cohort whose
  label is a *real* school year but whose date is unreadable is only repairable
  by correcting that year, not the current one. That is deliberate — history is
  not rewritten — but it means one recovery path still requires knowing which
  year to open.
