# Sprint 26 review — 27 August 2026

**Scope.** Marketing claims against product behaviour. Both findings correct,
and the first is not a copy defect. It is a live authorization hole, and the
most serious thing found in this repository.

---

## Finding 1 — the privacy promise had no code behind it

The product says, in two places I have myself edited and strengthened:

> *"An administrator sees aggregate figures only. There is no route in the
> product that shows an administrator a named student's answers."*
> *"A teacher sees their own roster."*

Neither was enforced anywhere. `requireStaff` accepts both roles, and every
teacher page and every teacher action checked only `classroom.school_id ===
user.school_id`. The consequences were live:

- **Two routes took an administrator to a named roster.** The class name on
  `/admin/classes` linked straight into `/teacher/class/[classId]`, and the
  teacher overview contained an explicit branch handing an administrator *every
  class in the school*, each with an "Open class" button. That page renders each
  child's display name beside their individual per-skill evidence.
- **Any teacher with another class's id could read and mutate it.**
  `requireOwnClass` — the guard on adding students, removing students and
  changing assignments — allowed any staff member in the school. A guessable URL
  and three callable server actions.

The second is the worse half. A link is not a permission model; server actions
are public endpoints whatever the UI renders.

### The fix

The rule is now a pure function in `src/lib/auth/access.ts` rather than a
condition repeated in six places:

```
canTeachClass(user, classroom)   // same school, role teacher, teacher of record
canAdministerClass(user, class)  // same school, role admin — the class as an object
```

`canTeachClass` **excludes administrators explicitly**, and the comment says
why: *"Administrators are deliberately excluded, not merely unrouted. The
product promises them aggregates, and a role check in one page loader is not a
promise — a promise is something no route can get round."*

Everything routes through it. The class page and both teacher surfaces gained
`requireTeacher`, which redirects an administrator to their own dashboard rather
than rendering the roster. The teacher overview lists only classes the user is
teacher of record for. `requireOwnClass` checks ownership. The admin class list
no longer links into the teacher page, and the class name is plain text with a
comment saying it is deliberately not a link.

One thing tightened beyond the finding: `createClassAction` read `teacherId`
straight from the form, so a teacher could create a class assigned to a
colleague. A teacher now creates only for themselves; an administrator may name
any teacher, because that is class identity.

**The administrator keeps the class as an object** — create, rename, archive,
delete, retention — and loses the roster and the evidence. `canAdministerClass`
cannot express access to either, which is the point of it being a separate
function.

### Verified in the running app

Signed in as the administrator, `/teacher/class/cls_room12` redirects to the
school overview. Signed in as Ms. Okafor, her colleague's `cls_room4` returns
404 and her own `cls_room12` renders normally.

## Finding 2 — the District plan sold three things that do not exist

Roster sync via Clever or ClassLink, district-level rollup reporting and single
sign-on were listed as District features. The README says all three are
deliberately deferred, the build runs one school, and staff sign in by email
with no password. The disclaimer said prices are illustrative — not that
features are unavailable — and an administrator can select District and see it
as the active plan.

The three capabilities moved out of the feature list into a dashed **"Not in
this build"** block on the card, footed with *"Production requirements for a
district deployment, not features you can use today."* The plans page's
"What this build does not do" section names them, and adds the sentence the
finding was really about: *"an evaluator reading a feature list is entitled to
assume the features are there."*

The plan selector gained its own note: **"Choosing District does not enable
anything."**

The future-tense sweep found two more. The class-code note and the privacy page
both said class codes are *"replaced by roster sync and single sign-on in a
district deployment"* — true of a roadmap, and read as a description of an
option you have. Both now say those would replace it in production, neither is
built, and the class code is how joining works here.

## Tests

Ten. The rule ones assert the pure function directly, because a rendered page is
the wrong place to prove an authorization model:

- The teacher of record gets in; a colleague does not; **an administrator does
  not**; another school does not; a missing class is refused rather than
  throwing at the call site.
- No role can both administer and teach the same class.
- `canAdministerClass` grants the admin the class and refuses the teacher.

And three that guard the wiring, because the rule existing is not the same as
every path using it:

- `/admin/classes` must not contain `/teacher/class/`.
- Both roster-bearing teacher pages must call `requireTeacher()` and must not
  call `requireStaff()`.
- Each mutating action must resolve its class through `requireOwnClass`, and the
  check inside it must be `canTeachClass` — the old `school_id !== school_id`
  comparison must not appear in the actions file at all.

**364 tests, up from 354.**

## What this says about the review process

Sprint 23 I rewrote the privacy notes to say precisely what the suppression
thresholds were, and asserted them. I never checked whether the *other* privacy
claim on the same page — administrators see aggregates only — had anything
behind it. It did not, and it had not since the page was written.

The checklist item from that sprint said *"a promise in the prose is a test
case"*, and I applied it to the one promise I happened to be editing. Applying
it to a promise is not the same as applying it to the promises.

There is a sharper version too. Every access-control question in this repository
had been answered "same school", and that was correct for the schema tests,
which is where access control had been tested. Nothing asked what a *role* may
do, because roles had never been the unit of the question. Twenty-five sprints
of review looked at what the product says and what it teaches; **this is the
first that looked at what it permits.**

## Deliberately left

- **Only the class-scoped surfaces were audited.** Classroom Mode, the mission
  library and the orientation are staff-level by design and show no student
  data, but nobody has walked every route asking who may reach it.
- **The claims on the approach, for-schools and privacy pages are still prose
  next to a separate implementation.** Three of them now have tests. The rest do
  not, and the honest position is that a claim without a test is a claim nobody
  has checked.
- Every mission has been read once, none twice.
