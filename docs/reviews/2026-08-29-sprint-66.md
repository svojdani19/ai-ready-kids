# Sprint 66 — risk conclusions the product could not support, and two inventories that were not the schema

**Date:** 2026-08-29
**Reviewed against:** HEAD `f9dc70c`
**Scope:** buyer-facing privacy and security copy, and the student data
inventory. No authentication change, no new student field, no telemetry, no
per-student admin view.

## 1. Three surfaces drew a risk conclusion instead of describing a control

| Surface | Claim |
| --- | --- |
| Public home | *"A first name and a last initial is the entire student record. Nothing to reset, nothing worth stealing."* |
| Admin → Classes | *"…which is exactly as much security as this data warrants."* |
| Public privacy | *"…the security is proportionate to that."* |

Each is a conclusion about risk, not a statement about what the software does,
and each sat on the same product that says elsewhere — accurately — that mission
and check-in records are **education records under FERPA**. A page cannot call
something an education record and dismiss access to it in the same breath.

They were also wrong about what the code reaches. Verified in the code, not
inferred:

- `src/app/join/[classId]/page.tsx` renders **every child in the class by name
  and avatar** to anyone holding a valid grant for that class.
- `src/app/actions/auth.ts` → `chooseStudent` writes a **student session** for
  any listed child, which opens that child's badges, finished missions and
  per-skill evidence.

So the code-holder does not merely reach "a child's own progress list". They
reach the roster, pick from it, and become the child they picked. A code is read
aloud to a room of seven year olds, who cannot meaningfully distinguish a shared
classroom credential from a personal one — which is exactly why the limitation
has to be described rather than reasoned away.

### The correction

`src/content/data-inventory.ts` → `CLASS_CODE_BOUNDARY`, said the same way
wherever codes are explained:

> A class code is shared classroom access, not proof of who is using it. It is
> typed by a room, not held by a person. · Anyone with the code can see that
> class's roster of first names and avatars, choose any child listed on it, and
> open that child's progress. · It reaches one class. It is not a way into
> another class, into a teacher's tools or into anything an administrator sees.
> · Rotate the code whenever it has travelled further than the class. The old
> code stops working immediately and nothing else about the class changes.

The third line is a real scope limit the product does enforce (grant is
per-class; `chooseStudent` refuses a student from another class), so it belongs
in a description of the boundary. It is not offered as a reason the first two
lines do not matter.

`CLASS_CODE_POSTURE` states the deployment posture once:

> Roster sync and single sign-on would replace class codes in a production
> deployment. Neither is built here, so a class code is the only credential in
> the product. That is enough for a **supervised pilot or a local
> demonstration**, where an adult is in the room and the roster is fictional or
> small and known; it is **not production access control**, and this build does
> not claim to be.

The home page card is now *"A class code, not a child's password"*. The existing
accurate statements — no password to reset, no recovery flow to attack, roster
sync and SSO not built — are kept.

## 2. Two "complete" inventories, neither of which was the schema

`/admin/data` listed six items under *"The complete list. There is nothing held
back."* `/privacy` listed a **different** six under *"Everything we hold about a
student."* Counting the columns of the three student-linked tables —
`students` (5), `attempts` (7), `benchmarks` (6) = **18**:

- the admin list accounted for **4 of 18**;
- the public list accounted for **7 of 18**.

Omitted by both: `attempts.evidence_json` (the derived per-skill
demonstrated/developing judgement), `benchmarks.started_at` /
`completed_at`, `students.created_at`, and every id and foreign key. Omitted by
the admin list alone: `students.class_id` — the class relationship, which the
public page did name. Two absolute claims, disagreeing with each other and with
`schema.ts`.

### The correction

One module both pages read: `src/content/data-inventory.ts`. Eleven entries,
each naming the `table.column` values it accounts for, and
`tests/data-inventory.test.ts` fails when any column of any student-linked table
is unclaimed — so a future `ALTER TABLE` breaks the build until somebody says
out loud what the new column is. That is what makes "every" checkable rather
than aspirational.

Scope is stated instead of assumed:

- **Admin:** *"Every column in the database that hangs off a student row, and
  the class and staff records those rows hang from. Not the school's own account
  settings, which are not student records."* The class/assignment/staff rows the
  old list already carried are kept, in their own labelled group.
- **Public:** *"That is every column in the database that hangs off a student
  row… It is not everything the product stores: a school's own account settings,
  its staff records and the audit log are not records about a child, and this
  list does not cover them."*

The public list stays student-scoped. Neither heading was expanded into a claim
about all product data, so neither had to grow to cover it.

## What was deliberately not done

- **No authentication change.** Class codes remain the only student credential.
  This sprint made the product describe that accurately; it did not fix it, and
  a fix is roster sync or SSO, which is a build, not a copy edit.
- **No new field, telemetry, per-student admin view, risk score, open text or
  auth.** The grades 2–4 authored niche is untouched.
- **The commercial limitation stands and is now stated on the page a buyer
  reads:** an administrator evaluating a paid pilot is being told, in the
  product, that anyone with a class code can open any listed child's progress,
  and that this is suitable for a supervised pilot rather than a production
  rollout. That is the honest position, and it will cost some deals. It is
  better than the alternative, which was a security claim the code did not
  support.
