# Sprint 79 — a parked class could still lose a child permanently

**Date:** 2026-08-30
**Reviewed against:** HEAD `39878a5`
**Scope:** `removeStudentAction` only, plus the test-suite reliability fix the
gate required. No new fields, telemetry or UI.

## The finding

`removeStudentAction` accepted an archived class. `requireOwnActiveClass` checks
ownership and the subscription term and never reads `archived_at`, so a teacher
calling the exported server action from a stale tab or a direct request could
**permanently delete one child** out of a parked cohort, cascading to every
attempt, check-in and badge they had.

That contradicts three things the product says at once: archiving keeps the
roster and records until a restore, retention deletes on a schedule the school
sets, and an administrator's explicit deletion is the other way records go. None
of them anticipated a fourth door into a class nobody is teaching. The damage is
also invisible — the class is parked, so nobody is looking at it, and a school's
history and exports quietly stop matching the year they describe.

This is the destructive member of the group named at the end of sprint 76, where
`setAssignmentAction` was fixed and `renameStudentAction`, `removeStudentAction`
and `rotateJoinCodeAction` were listed as unaudited.

## The correction

After the owned, active-term class is resolved and **before** `auditedWrite`:

```ts
if (classroom.archived_at) {
  return { error: REMOVE_STUDENT_CLASS_ARCHIVED };
}
```

> That class is archived. Restore the class before removing a student from it.

`requireOwnActiveClass` is deliberately **not** widened — that would change every
classroom mutation at once — and rename and rotate semantics are untouched.

## Acceptance evidence

Three tests through the **real exported action** with a real teacher session:

| Test | Proves |
| --- | --- |
| refuses removal while archived | the message, distinct from `REMOVE_STUDENT_FAILED` and from the mismatched-pair refusal; the class row, the child's row, the roster around them, **their attempts, their check-ins**, all attempts, all benchmarks and every audit row byte-identical; zero `roster.removed` |
| refuses above the transaction | with a `roster.removed` audit trigger **armed**, the result is still the archived message and not `REMOVE_STUDENT_FAILED` — proving nothing was attempted and no write lock taken |
| succeeds after restore | `restoreClass` then the same removal works, with the existing atomic behaviour intact: the cascade checked by the child's id captured **before** the delete, and exactly one `roster.removed` audit |

Badges and skill evidence are covered by the attempt rows, which is where both
live.

**Mutation-checked:** removing the refusal fails all three; moving it *inside*
`auditedWrite` also fails all three.

## The gate was unreliable, and this is what it was

Twice before I called intermittent failures "contention" and moved on, and once
I raised the global timeout on an unverified inference and then withdrew it.
This time the error text was captured first:

```
FAIL tests/admin-journey.test.ts > counts students in every active class …
Error: Test timed out in 5000ms.
```

A timeout, not a race — and on tests that are a handful of synchronous
`createStudent` calls, which cannot race at all. Then each hypothesis was tested
rather than assumed:

| Hypothesis | Test | Result |
| --- | --- | --- |
| The dev server was competing | stopped it, ran ×5 | **worse** — 4 of 5 runs failed |
| Fork oversubscription | `maxForks: 4`, ran ×5 | **no help** — 5 of 5 runs failed |
| Machine overload | `uptime`, `ps` | load 3.9 on 8 cores; not enough to stall a millisecond test |
| Fixture cost | measured | `openDatabase` 6ms, `seed` 130ms; not the cost |
| **fsync stalls on throwaway databases** | `PRAGMA synchronous = OFF` in `createTestDb` | **10 of 10 runs clean** |

The schema sets WAL, which fsyncs on every commit, and this suite commits
constantly — the seat check, the purge and every audited write open
`BEGIN IMMEDIATE`. When the disk stalled, trivial tests blocked past 5s and
failed as timeouts, wandering around the suite at random.

A test database is deleted moments after it is created, so durability is the only
thing given up. Every transaction, lock and rollback still behaves exactly as in
production, which is what these tests are about. **No timeout was raised and no
production code was touched** — the 5s default stands, so a genuinely slow test
or a real hang still fails.

## Known gaps

- **`renameStudentAction` and `rotateJoinCodeAction` still accept an archived
  class.** Neither destroys anything — a rename is reversible and a rotation
  changes a credential nobody can currently use — so neither was in this sprint,
  and both remain unaudited for the parked-then-restored reasoning.
- **The refusal is per-action, three times over now.** `setAssignmentAction`,
  `removeStudentAction` and a growing list each carry their own `archived_at`
  check. A resolver that took the caller's intent — reads, reversible writes,
  destructive writes — would be the durable shape, and is a refactor rather than
  a correction.
- **The suite's speed still depends on the machine.** Removing fsync bought a
  large margin, but the heaviest tests seed a whole demo school per fixture and
  nothing caps how long that may take.
