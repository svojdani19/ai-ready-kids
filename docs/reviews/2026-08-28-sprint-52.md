# Sprint 52 — one classroom, or thirty students?

**Date:** 2026-08-28
**Scope:** the active-class limit for the classroom plan. No billing, no new
plan system, no LMS/SIS work.

## The finding

The public page sells **"Single classroom · $390 / year · Up to 30 students"**,
and only the thirty was enforced. `licensed_students` had a gate from sprints
42–43; the *classroom* had none.

So a school on the classroom plan could create any number of classes, split its
thirty children across them, archive one and create another, and restore
archived cohorts whenever the roster total stayed under thirty. `createClass`
had no plan check at all, and `restoreClass` checked only students.

**The product sold one classroom and licensed thirty students, which are
different things.** A buyer could not tell what $390 entitled them to, and the
vendor was giving away the difference — a three-form-entry school could run the
whole year on one classroom licence.

## The rule

`ACTIVE_CLASS_LIMIT` in `src/lib/repo/entitlement.ts`: `classroom: 1`,
`school: null`, `district: null`. `null` rather than a large number, so the
intent is legible — school and district are sold *per school* and *per
district*, and the number of rooms is not what they are priced on.

**Archived classes do not consume the slot**, for the same reason they do not
consume seats: a cohort kept for retention is not a class in use, and charging
for it would push an administrator toward deleting records early to free
capacity.

## Enforcement

At the repository write boundary, in **both** paths that can take the slot, each
with the count and the write inside one `BEGIN IMMEDIATE` transaction:

- `createClass` — assert, then insert.
- `restoreClass` — the room before the seats, so a classroom-plan school with a
  class already running hits the room limit first. Guarded on
  `classroom.archived_at`, so **re-restoring an already-active class stays a
  no-op** rather than counting itself twice and refusing a change that changes
  nothing.

The check reads "is there room for one more", not "is this school over its
limit" — which matters for the next point.

## Nothing is ever taken away

A database can already be over the limit: from a plan downgrade, or from before
this rule existed. **Nothing deletes, auto-archives or picks a class.** The
state becomes read-only — the next class is refused with an explanation — and
every existing class and record stays exactly where it is until an administrator
reduces the active classes or the entitlement changes. A test builds that state
deliberately (three active classes on a one-room plan) and asserts all three
survive.

## The refusal

One sentence of fact, one of reassurance, one route out — shared by both flows so
they cannot drift:

> The Single classroom plan includes one active class, and this school already
> has 1. Creating another class would make 2. Nothing has been changed, and every
> archived class and all of its records are still here. Archive the active class
> to free the slot, or ask for a quote on the Program and plan page.

An expected `{ error }`, not an error page. The audit records
`class.blocked_by_plan` / `class.restore_blocked_by_plan` with **school and
class configuration facts only** — how many rooms, on which plan — and **no
child is named**. No success audit is written on either refused path.

## Visible before the form

- **Program & plan**: an *Active classrooms* stat reading `1 of 1`, with
  *"Archive one to add another"* when full and *"Archived classes do not count"*
  otherwise.
- **Classes screen**: the same fact as the Create-a-class panel description, so
  it sits next to the form that would spend it.

## Tests

Eleven cases in `tests/admin-journey.test.ts`, **all confirmed to fail without
the rule** by stashing the source: first class allowed and second refused with
zero class rows written; archiving frees the slot and the archived records
survive; restore refused while another is active with the archived class on its
original timestamp; restore succeeds once the slot is free; re-restoring an
active class is a no-op; school and district allow three; an already-over
database is left intact; the two write paths cannot oversubscribe the slot in
either order; both repository functions carry `assertRoomForActiveClass`,
`BEGIN IMMEDIATE` and `ROLLBACK`; the refusal wording and the audit's silence
about children; and a **drift guard** binding the public copy (*"Single
classroom"*, *"per classroom, per year"*, *"$390 / year"*) to
`ACTIVE_CLASS_LIMIT.classroom === 1`, with every plan the selector offers
required to have a decision recorded.

**588 tests, up from 577.**

## Verified in the browser

Demo school temporarily on the classroom plan with one active class and three
archived, at **1280×800** and **768×1024**:

- Program & plan: **`Active classrooms: 1 of 1` · "Archive one to add another"**.
- Classes: **`Active classrooms: 1 of 1. Archived classes are kept and do not
  count.`** on the create panel.
- **Create refused** with the full sentence, no error page, still 4 classes.
- **Restore refused** the same way, class still tagged Archived.
- Database after both: `Room 12 [active], Room 14/21/4 [archived]`, **exactly two
  audit rows added**, both configuration facts, no child named, no success audit.
- **Archiving the active class freed the slot**, and Room 4 then restored with no
  refusal.
- No horizontal overflow at either size.

Demo restored: `plan school`, 120 seats, four active classes, 90 students, 16
audit rows.

## Preserved

No chatbot, child free text, new student fields, telemetry, risk scoring or
payment data. No schema change — `plan` already existed. Seat enforcement,
retention, the lapse gate and every allowed path are untouched.

## Observed, not built

- **A downgrade is not blocked.** Nothing stops a school moving from `school` to
  `classroom` while three classes are active; the result is the read-only state
  above rather than a refusal at the point of change. Since the plan is
  vendor-set, that is arguably the right place for the conversation to happen —
  but it is a judgement call.
- **Only rooms and seats are metered.** Teachers, assignments and archived
  cohorts are unlimited on every plan, which matches what is sold today.

## The lesson

**A price with two numbers in it needs two enforcements.** "One classroom, up to
thirty students" is a conjunction, and the product enforced the half that was
easy to count. The gap was invisible from inside the code — `licensed_students`
had a gate, so entitlement *looked* handled — and visible immediately from the
sales page, which is where this finding came from.

Where public copy states a limit, the words and the enforcement want binding
together in a test, or one of them moves alone.

# Sprint 53 — the correction: the gate failed open on bad data

Independent review rejected sprint 52 on one fail-open contradiction. It is
mine, and it is the worst kind: the gate held for every correct input and let go
exactly where the data was wrong.

## The defect

Two lines, in different files, that only became a hole together:

```ts
limit: ACTIVE_CLASS_LIMIT[school.plan] ?? null          // unknown → no limit
const planLabel = … : school.plan === "district" ? … : "Classroom"   // unknown → "Classroom"
```

`schools.plan` is unconstrained `TEXT`, set by the vendor outside the UI. So a
typo, a migration defect or a stale value such as `"classrooms"` was **shown to
the administrator as the Classroom plan while receiving no limit at all** —
unlimited active classrooms, on the cheapest plan name.

**The paid gate failed open precisely when the entitlement data was malformed**,
which is the one condition where it most needs to hold. And it contradicts the
codebase's own settled direction: sprint 34's schema classifier fails *closed*
on an unrecognised database, and that sprint's review argued the case in as many
words. I wrote the opposite here without noticing.

`??` is what made it invisible. It reads as a default, and for an entitlement a
default is a grant.

## The correction

**The lookup cannot coalesce.** `ACTIVE_CLASS_LIMIT` is `as const satisfies
Record<string, number | null>`, with `isKnownPlan` as the only way in.
`classroomAllowance` now returns `recognised: boolean`, and an unknown plan gets
**`limit: 0`, never `null`** — zero grants nothing, `null` means unlimited, and
a lookup miss must never be able to reach the second one. A test asserts the
`??` shape is absent from the source entirely.

**No unknown value is ever labelled.** `planLabel()` returns the plan's real
name or `"Plan needs configuration"`, and a test forbids `: "Classroom"` in
either admin page so the ternary cannot come back.

**It fails closed, and takes nothing away.** `assertRoomForActiveClass` throws
`PlanNotRecognisedError` — distinct from `ClassroomLimitError`, because it is a
different conversation: the school has not exceeded anything, the record is
wrong. Create and restore are refused. **Nothing is auto-archived, deleted or
chosen**, and every existing active and archived class keeps its records and its
timestamp.

**The message says what is actually true**, and is not the Single classroom one:

> This school's plan could not be verified, so no new classrooms can be
> activated. Creating a class has been declined and nothing has been changed —
> every class, archived class and record is exactly as it was. Ask Rosa Delgado
> to have the plan corrected on the account, and this will start working again.

Audited as `class.blocked_by_plan_config` /
`class.restore_blocked_by_plan_config`, configuration facts only, no child
named, no success audit on the refused path.

**The pages say so plainly.** Program & plan shows **Plan: "Plan needs
configuration"** in the alert tone with *"Ask your account contact to correct
it"*, and **Active classrooms: 3** with *"No new classrooms can be activated"*.
The Classes create panel reads *"Plan needs configuration — no new classrooms
can be activated. 3 active, and every class and record is unchanged."*

**Read-only and ownership paths are untouched**: listing, archiving, deleting and
exports all still work, because a school owns its records whatever its plan
field says. A test asserts archive and delete still succeed under a bad plan.

**classroom = 1 and school/district = unlimited are exactly as implemented in
sprint 52.** Only the unknown case moved.

## Coverage

Eight cases, **nine failing against the sprint-52 code** when the source is
stashed. Six malformed values are swept — `"classrooms"`, `"Classroom"`, `""`,
`"site"`, `"school "`, `"premium"` — asserting `recognised: false`, `limit: 0`
and never `null`; no `??` on the lookup; no page containing `: "Classroom"`;
create and restore refused with every class and record preserved on its original
timestamp; the message distinct from the Single classroom one; the audit's
silence about children; `PLAN_LABEL` and `ACTIVE_CLASS_LIMIT` required to have
identical keys, so a new plan cannot arrive with a limit and no label.

The `??` guard tripped on its own first draft by matching the comment that
explains the old expression — sprints 44 and 51 again — so it strips comments
before scanning.

**596 tests, up from 588.**

## Verified in the browser

Demo school set to `plan = 'classrooms'`, three active classes and one archived,
at **1280×800** and **768×1024**:

- **Program & plan**: `PLAN | Plan needs configuration | Ask your account contact
  to correct it` and `ACTIVE CLASSROOMS | 3 | No new classrooms can be
  activated`. No crash, no "Classroom", no overflow.
- **Classes**: the configuration panel text, **create refused** with the
  verification message, **restore refused** the same way, class still tagged
  Archived, still 4 classes.
- Database after both: `Room 12/14/21 [active], Room 4 [archived]`, **90 students
  intact**, **exactly two audit rows added**, both configuration facts.

Demo restored: `plan school`, 120 seats, four active classes, 90 students, 16
audit rows.

## The lesson

**`??` on an entitlement lookup is a grant with a default's syntax.** It reads
like a sensible fallback and means "when we cannot tell what you bought, assume
the most generous answer". The safe direction for unknown state was already
settled in this codebase, in writing, and I still reached for the operator that
does the opposite.

The sharper version: **a limit and its label must come from the same source.**
These were two independent expressions about one fact, and each was individually
defensible — the ternary needed *some* final branch, the lookup needed *some*
fallback. It was the pair that lied, showing the cheapest plan while granting
the most expensive behaviour, and neither file could see the other.
