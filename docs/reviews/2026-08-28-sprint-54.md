# Sprint 54 — the window that could delete children's records early

**Date:** 2026-08-28
**Scope:** retention policy validation and the purge job's failure mode. No
schema, no new fields, no scope beyond making a bad value safe.

## The finding

`schools.retention_months` is unconstrained integer data. The form only ever
writes 3, 12, 24 or 36, but a vendor edit, a migration defect or a stale value —
`-12`, `0`, `7`, `120` — was accepted by the domain and passed straight to
`addMonths`.

A **negative** window moves a cohort's deletion date to *before* its school year
ended. Every class becomes `eligibleNow`, and `runScheduledPurge` then deletes
the class and cascades **the roster, every attempt and both check-ins**. The
Data page displayed the bad value as if it were policy, so nothing warned
anybody.

This is not access or revenue. **A scheduled job could permanently destroy
children's education records, with no restore path**, because one integer was
wrong.

## The rule

`RECOGNISED_RETENTION_MONTHS` is derived from `RETENTION_OPTIONS`, so the
windows the form offers and the windows the domain accepts are one list.
`isRecognisedRetention` requires a number, an integer, and membership.

**Nothing is repaired.** Not coerced, not clamped, not rounded, and above all
not defaulted to twelve: a guess that lands early deletes a child's records
before the school's own policy said it would, and a guess that lands late
retains them past it. Neither is this code's decision — the same reasoning
sprint 32 applied to a missing year-end, and the direction sprints 34 and 53
settled for unrecognised state.

## Fail closed, per school

`runScheduledPurge` skips a school with an unrecognised window **before reading
or writing anything for it**, records it in `result.blocked` with the school
name and the stored value, and `continue`s — so **one school's broken record
never stops a correctly configured school purging on the date its policy
actually says**. No `retention.purged` audit is written for a blocked school,
because none happened.

The blocked entry names a school and a number and **no child**: which school has
a bad account record is not a fact about any pupil.

## Two blocks, not one

`RetentionRow` gains `blockedReason: "unrecognised-policy" | "no-year-end" |
null`. These are different situations needing different sentences and different
people — a missing year-end is an administrator finishing a migration; an
unrecognised window is a broken account record. `purgeDateFor` and
`purgeDateForClass` return `null` for both, so no date is ever calculated from a
window the product does not sell.

## What an administrator sees

- **Retention window**: *"Needs configuration"* in the alert tone, with *"The
  stored value is -12, which is not one of the windows below. Automatic purge is
  blocked until you choose one."* The malformed number is named as **a stored
  value**, never rendered as policy.
- **This year due**: *"Blocked"*, with *"Nothing is deleted automatically while
  the retention window needs configuration."*
- **Per class**: *"Retention needs configuration — automatic purge is blocked."*
  No class is marked eligible.
- **Delete now stays available**, with its existing two-step confirmation. It is
  a deliberate administrator action, not automatic retention, and blocking a
  school's own ability to delete its own records would be the wrong direction.
- **Recovery**: the form validates against `RETENTION_OPTIONS` already, so
  saving a recognised value unblocks immediately. **Viewing the page does not
  overwrite the bad value** — no radio is preselected, and nothing writes on
  render.

## The CLI cannot be misread

A safety block and a quiet night both produce zero deletions, and in a log they
looked identical. The blocked list now prints to **stderr**, after the summary,
naming each school and its stored value, and sets **`process.exitCode = 1`** so
a scheduler notices rather than logging it into nothing.

## Tests

Eight cases, **all eight failing against the previous code** when the source is
stashed.

- The recognised set is exactly `[3, 12, 24, 36]` **and equals what
  `RETENTION_OPTIONS` offers**, so the form and the domain cannot drift.
- A sweep of `-12, 0, 1, 7, 120, -1, 2.5, NaN` plus `"12"`, `null`, `undefined`,
  `{}`, `[]` — all unrecognised; no date from `purgeDateFor` or
  `purgeDateForClass`; `retentionBlock` reports `unrecognised-policy`.
- With `-12`, **no row is `eligibleNow`** — which without the guard would be all
  of them — and every row reports the policy reason rather than the year-end one.
- The job deletes **zero classes, students, attempts and check-ins** for every
  storable malformed value, writes **no `retention.purged` audit**, and reports
  the school as blocked. Counts are compared table by table before and after.
- **A second, correctly configured school still purges in the same run** while
  the malformed one loses nothing, and the blocked report names no child.
- Saving a valid window **resumes purging**.
- 3, 12, 24 and 36 behave exactly as before.
- A drift guard: the job checks before it deletes, `retention.ts` contains no
  `||`, `??` or `Math.max/min/round` on the stored value, the CLI carries
  `BLOCKED` and `process.exitCode = 1`, and the page keeps both the blocked
  sentence and the manual Delete controls.

One honest note recorded in the test: **`NaN` is not representable** — SQLite
rejects it against the NOT NULL column — so it is swept through the pure
functions and not through the job. The column's own constraint rules that one
out; it does not rule out the others.

**604 tests, up from 596.**

## Verified

**The CLI, against a real database with `retention_months = -12`:**

```
Nothing is past its retention date. No records were deleted.

BLOCKED: 1 school skipped because the retention window is not one this product
recognises. No records were deleted for them, and nothing has been changed.
  - Brightwood Elementary School: retention_months is -12, which is not 3, 12,
    24 or 36. Set a policy on the Data and retention page.
```

Exit code **1**. Afterwards: **4 classes, 90 students, 885 attempts, 134
check-ins — all intact — and 0 `retention.purged` audit rows.** With a valid
window the same command exits **0** and prints only the summary.

**Browser at 1280×800 (`-12`) and 768×1024 (`7`):** no crash; *"Needs
configuration"* with the stored value named; *"Blocked"*; the per-class notice;
**nothing marked eligible**; `-12 months` / `7 months` never shown as policy;
**Delete now still present** and not clicked; no overflow. Selecting 12 and
saving recovered at both sizes — *"Retention set to 12 months after the school
year ends."* and the window reading `12 months` again.

Demo restored: retention 12, plan school, 120 seats, four active classes, 90
students, 885 attempts, 16 audit rows.

## Observed, not built

- **The column is still unconstrained.** This makes a bad value safe, visible and
  recoverable; it does not prevent one being written. A CHECK constraint needs a
  migration, which was out of scope.
- **`benchmark_window` has a CHECK constraint; `licensed_students` and
  `plan` do not.** Sprint 53 made `plan` safe and this makes
  `retention_months` safe. `licensed_students` remains unaudited for the same
  shape — a negative or absurd seat count would not delete anything, but it has
  not been checked.

## The lesson

**The danger of a value is not how likely it is to be wrong, but what happens
when it is.** The plan defect leaked revenue; this one deleted children's
records. Same shape — unconstrained data trusted by a calculation — and three
orders of magnitude apart in consequence.

So the audit worth doing is not "which columns are validated" but **"which
columns feed something irreversible"**. There is exactly one irreversible
operation in this product, and until now the number that scheduled it was
accepted without being read.
