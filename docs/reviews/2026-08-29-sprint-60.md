# Sprint 60 — the calendar that produced Invalid Dates and hid them

**Date:** 2026-08-29
**Scope:** academic-calendar validation and everything downstream of it. No
schema, no new fields, no platform work.

## The finding

`setAcademicDatesAction` checked only the regex **shape**, so `"2026-13-45"` and
`"2026-02-30"` were saved to the school **and backfilled into every class in that
year**. The ordering guard passed too — comparing two Invalid Dates gives `NaN`,
and every comparison against `NaN` is false, so `endsOn <= startsOn` was
cheerfully false for two nonsense dates.

Three separate failures downstream, and the third is the serious one:

1. **`addYear` threw `RangeError`**, taking the Program page down — the only
   place an administrator can correct the dates. The recovery surface was the
   thing that broke.
2. **`purgeDateForClass` returned an Invalid Date.** `retentionRows` marked the
   row unblocked because the string was merely non-empty, so Data displayed
   *"Invalid Date"* as if it were a schedule.
3. **The purge job then compared `NaN <= now`**, found it false, skipped the
   cohort and exited saying nothing was due. **A child's records retained
   indefinitely, reported as success.**

Plus: `academic_year` accepted `"2025-2027"` on shape alone; a class snapshotted
the label and the year-end without verifying either; correcting the school only
repaired cohorts whose date was exactly `""`, so a malformed snapshot had **no
recovery path at all**; and `SchoolReport` exported the raw label as a factual
reporting period.

## One rule, extracted

`src/lib/domain/calendar.ts` holds it, and sprint 58's `isContractDate` now
*is* `isCalendarDate` rather than a second definition — two validators for "is
this a real day" drift, which is the whole failure this addresses.

- **A date** is exactly `YYYY-MM-DD` and round-trips through UTC. `2026-02-30`
  parses to March 2nd and does not stringify back; `2024-02-29` does.
- **A year label** is exactly `YYYY-YYYY` and consecutive.
- **The pair is ordered** (`start < end`, strictly) **and inside the two years
  named** — a "2025-2026" running 2019→2031 is not a school year, and every
  cohort created under it would snapshot a deletion date from a calendar nobody
  recognises.

`academicProblem` returns which of the five things is wrong, and the message for
each **never quotes the stored value back**.

## Nothing downstream can produce an Invalid Date

- `purgeDateFor` / `purgeDateForClass` validate rather than test for emptiness,
  and return `null` — never an Invalid Date, which is worse than no date because
  it renders, compares false against everything, and looks like a schedule.
- `RetentionBlock` gains **`malformed-year-end`**, distinct from `no-year-end`:
  one is an administrator mid-migration, the other a broken record silently
  retaining a child's records for ever.
- `previewRollover` validates the whole calendar before any formatting or
  arithmetic and returns *"Academic dates need configuration"* with the specific
  correction. `addYearOrNull` exists so nothing can throw on stored data.

## The purge blocks instead of skipping

`runScheduledPurge` reports malformed cohorts in `blockedCohorts` — **per school,
as a count**. No class name, no child, no raw value: which school has broken
records is operational; which class is not the operator's business. Valid due
cohorts in the same school **still purge**, so one bad snapshot does not stop a
school's schedule.

The CLI guards its all-clear on **both** kinds of block (`anyBlock`) and exits
`1` for either, so sprint 55's lesson holds for the new case.

## Recovery, scoped honestly

`setAcademicDates` now repairs **empty and malformed** year-ends — the widening
that gives a malformed cohort a path back — but only in **that school** and
**that academic year**, and only rows whose date is not already a real day. An
already-valid snapshot is a deliberate record of when that year ended and is not
moved; neither is any other year. The audit and the success message say exactly
that, with a count.

Class creation refuses before writing anything when the school's calendar is
unreadable, because a new class copies the label and the end date and would be
minted unschedulable. Staff-only wording, and it says plainly that existing
classes and student work are unaffected.

## Tests

Fifteen cases in a new `tests/academic-calendar.test.ts`, **eleven failing
against the previous code** when the consumers are stashed. Sweeps `""`, `" "`,
`"2026-13-45"`, `"2026-02-30"`, `"2026-9-1"`, leading and trailing whitespace, a
timestamp, `"26-06-12"`, `"2026/06/12"`, `"soon"`, plus `null`, `undefined`, a
number, `{}` and `[]`; non-consecutive and reversed labels; `start >= end`; dates
outside the labelled span; valid leap days; mixed valid/invalid cohorts; the
partial purge with a refusal snapshot; repair scope across three cohorts and a
second year; rollover never throwing; buyer and export safety; and recovery.

**656 tests, up from 641.**

## Verified in the browser

At **1280×800** and **768×1024**, with the school on `academic_year =
"2025-2027"` / `year_starts_on = "2026-13-45"` and Room 14 on `"2026-02-30"`:

- **Program renders**, with the correction form present and **no `Invalid
  Date`, no `NaN`, no raw value**. The panel reads *"Academic dates need
  configuration. Retention and rollover are blocked until the year and both
  dates are set below."* The rollover preview is suppressed rather than throwing.
  The form does **not prefill** the malformed values — sprint 56's precedent.
- **Data & retention**: Room 14 shows *"Blocked"* and *"This cohort's year-end
  date cannot be read… Save the academic dates on Program & plan to repair it"*,
  nothing marked eligible, no raw value.
- **Class creation refused** with the staff message, still 4 classes.
- **JSON/CSV**: `schoolYear: "Needs configuration"`, and **no** `2025-2027`,
  `2026-13-45` or `2026-02-30` in either.
- **The purge, with three overdue valid cohorts and one malformed**: deleted
  *Room 4, Room 12, Room 21* and 68 student records, then
  `BLOCKED: 1 cohort across 1 school…` naming the school and a count only, exit
  **1**. The malformed cohort survived untouched.
- **Recovery**: saving 2025-2026 / 2025-08-25 / 2026-06-12 returned *"Saved. 1
  class in 2025-2026 had no usable deletion date and now has one. Classes with a
  valid date were left unchanged."* Rollover reappeared, and the database showed
  Room 14 repaired with the other three unchanged.

Demo restored with `npm run db:reset`: 1 school, 6 staff, 4 classes, 90 students,
53 assignments, 884 attempts, 134 check-ins.

## Observed, not changed

- **The columns remain unconstrained.** Safe, visible and recoverable; not
  prevented. A CHECK constraint needs a migration.
- **One pre-existing test is intermittently timing-sensitive** — *"offers Try
  again, and advances once the retry succeeds"* in the mission player failed once
  and passed on four consecutive re-runs. Unrelated to this work, but it is a
  flake and it should be nailed down rather than tolerated.

## The lesson

**An Invalid Date is worse than no date.** A missing value announces itself:
every guard in this codebase already tested for empty, and the pages said "not
set". An Invalid Date passes the emptiness check, renders as text, and compares
false against everything — so it looked like a schedule, and the one comparison
that mattered silently answered "not due yet, and never will be".

The general form: **a sentinel that participates in your operations is more
dangerous than one that refuses to.** `null` would have thrown or shown "not
set" somewhere obvious. `new Date("2026-13-45")` cooperated with every call and
lied about all of them.

# Sprint 61 — the correction: the recovery missed the cohort it was for

Independent review withheld acceptance on the repair query, and the state it
misses is precisely the one sprint 60 was written to fix.

## The defect

`setAcademicDates` updated the school **first**, then selected classes with
`school_year = <the new label>`. But a class created while the school said
`"2025-2027"` copied **that** label along with the broken date. So:

- school `academic_year = "2025-2027"`, `year_ends_on = "2026-13-45"`;
- a cohort carrying `school_year = "2025-2027"`, `year_ends_on = "2026-13-45"`;
- the administrator saves a correct 2025-2026 calendar;
- the query looks for `"2025-2026"` and does not find that cohort.

Data still said **Blocked**, the purge still exited **1**, and there was no
correction path from anywhere. Sprint 60 claimed a recovery path it did not have
for the exact case it described.

## The correction

**Read the previous label before writing.** The repair now covers the new label
always, and additionally the previous one **only when that previous label was
itself unrecognised** — such a cohort could only exist by copying a broken
school label, which is the invariant class creation has always had. A previous
label that was a real school year is history and is never rewritten; a test
asserts that directly.

Within those labels: cohorts are relabelled onto the corrected year, and **only**
missing or malformed year-ends are repaired. A valid snapshot is a deliberate
record of when that year ended and is kept even on a cohort being relabelled.

**Two counts, reported separately**, because one number standing for two
different things is checkable as neither:

> Saved. 1 class moved onto 2025-2026 from a school year that could not be read,
> and 1 class given a usable deletion date. Classes with a valid deletion date
> kept it, and other school years were not touched.

One more leak closed while here: the Data table rendered the **cohort's own**
label, which can be malformed for the same reason. The class name already
identifies the row, so the label now reads *"Year needs configuration"* rather
than `2025-2027`.

## Coverage

Two cases added, four failing against the sprint-60 repair. The first builds the
exact state above with two controls — a cohort under the same broken label but
with a **valid** date (relabelled, date kept) and a cohort under a **real**
historical year (untouched) — then proves retention unblocks for every row,
rollover returns, and `runScheduledPurge` reports **no** blocked cohorts. The
second proves an ordinary year-to-year change relabels nothing, even when last
year's cohort has an empty date.

**658 tests, up from 656.**

## Verified in the browser

At **1280×800** and **768×1024**, from the exact legacy state:

- Data showed *Room 14 · Grade 3 · Year needs configuration · Blocked* with the
  repair instruction, and **no raw value** anywhere.
- Saving 2025-2026 / 2025-08-25 / 2026-06-12 returned the two-part message
  above; rollover reappeared.
- Afterwards every cohort read `2025-2026 / 2026-06-12`, Data showed **nothing
  blocked**, and `npm run purge` printed *"Nothing is past its retention date"*
  and exited **0**.

Demo left at 2025-2026 / 2025-08-25 / 2026-06-12, four classes, 90 students, 884
attempts, 6 audit rows.

## The residual limit, stated plainly

Recovery is anchored to the school's **previous** label. If an administrator
corrects the school first and only later notices a stranded cohort, the previous
label at that moment is already valid, so the cohort is no longer reachable — a
second save reports *"Saved."* and repairs nothing. I have **not** broadened the
match to "any unrecognised label in this school" on my own judgement: it would
also sweep cohorts from a different broken era onto the current year, which is a
data decision rather than a bug fix, and the scope for this correction was
explicit. Flagged for direction rather than taken.

## The lesson

**My own test constructed the state I had already fixed.** The sprint-60
recovery case built its cohorts with `school_year: "2025-2026"` — the corrected
label — and so exercised a database that could only exist *after* the fix it was
meant to prove. The legacy shape, where the cohort carries the broken label
because it copied it, never appeared.

When a fix is for records written by the old code, the fixture has to be written
the way the old code wrote them. A test built from the new invariants tests the
new invariants.
