# Sprint 30 review — 27 August 2026

**Scope.** Two load-bearing privacy claims. Both findings correct. Sprint 27
made the class code enforceable; this one makes it worth enforcing, and gives
the retention date a mechanism it never had.

---

## Finding 1 — the credential was cheaply enumerable

Sprint 27 fixed possession: entering the code writes a signed, class-bound
grant, and the roster page and `chooseStudent` both verify it. That was the
right fix for the wrong-shaped hole. **The code itself was one word from a list
of fifteen plus three digits — 13,500 possibilities, from `Math.random`.**

`findClassByCode` is a public, unthrottled server action that searches every
active class. At school scale a live code falls out in far fewer than 13,500
attempts, and one hit hands over a roster and then any child's session. And a
code that had been photographed or passed around stayed valid all year, because
the only way to change one was to delete the class and rebuild it — taking every
roster and record with it.

### What changed

**Entropy.** Two distinct words plus three digits, drawn with `randomInt`, from a
64-word list chosen to be readable, sayable and typeable by a seven-year-old:
distinct on sight and on the ear, no near-homophones, nothing a single letter
away from another entry. `MAPLE-HERON-317`. A little over **3.6 million**
combinations, and still three chunks a child reads off a board — case- and
punctuation-insensitive, so `maple heron 317` works.

**Cost per guess.** A progressive backoff limiter: five free attempts, then
doubling delay to a sixty-second ceiling, cleared the moment somebody gets in,
because a child who succeeds is not suspicious. What it deliberately is not is a
profile — an in-memory counter and a timestamp keyed by a coarse bucket, nothing
written to the database, nothing surviving a restart, no identifier of a child
anywhere near it. **A per-process counter is exactly as good as one process**,
so the README states plainly that a real deployment does this at the edge.

**Non-enumerating errors.** A wrong code and an archived class have always
returned the same sentence; a test now pins that there is exactly one such
message in the function.

**Rotation.** A teacher can change a class code from the class page without
deleting anything. The grant carries the code it was issued against, so
rotating invalidates outstanding grants immediately — including one held by
somebody halfway through joining. Audited.

## Finding 2 — the retention date had no mechanism

The administrator page said **"Scheduled purge"** and **"Deletes on"**. The
privacy page said *"deletion is a date"*. The plans page sells retention
controls. The school report says data is deleted on the school's schedule.

The only thing that deleted anything was an administrator clicking **Delete
now**. `eligibleNow` changed a label from grey to red. Records could sit
indefinitely past the date families had been shown.

The finding offered two honest resolutions. I took both halves, because either
alone leaves something untrue: **build the mechanism, and stop calling it
automatic while nothing automatic runs it.**

`runScheduledPurge` deletes every class past its date with each roster, attempt
and check-in, and writes an audit entry attributed to "Retention job". It is
idempotent — a second run deletes nothing — and it compares **dates in UTC**, so
a class becomes eligible at the start of its purge day rather than at an hour
that depends on where the job ran. `npm run purge` is the entry point.

It is written against SQL rather than the repository layer, for the same reason
the seed is: it runs from a script, outside the request lifecycle, where the
`server-only` guard applies and should not be worked around.

And the copy now matches. **"Deletion due"**, not "Scheduled purge". **"Due
on"**, not "Deletes on". The page carries a note saying what runs it, that it is
idempotent, and — the sentence that makes the rest honest — *"Nothing in this
build runs it on a timer: a deployment schedules it, and until it runs, records
past the date are still here. That is why this page says due rather than
deleted."* The privacy page, the for-schools page and the README say the same.

## Tests

Eighteen. The credential ones cover entropy and format, that two hundred draws
essentially never collide, that a code never repeats a word, and that it stays
typeable. The throttle ones cover the free allowance, progressive backoff, the
block expiring, forgiveness on success, bucket isolation, and that nothing
persists. Rotation covers the class surviving, the roster surviving, an old
grant becoming unusable, and a missing class.

The purge ones are the boundary cases the finding asked for: nothing the day
before, everything on the day itself **at one minute past midnight UTC**,
cascades verified through attempts and check-ins, the audit entry, and a repeat
run that deletes nothing and adds no audit noise. Plus a copy assertion that the
page says "Deletion due" and does not say "Scheduled purge" or "when it
disappears".

**419 tests, up from 401.**

## What this says about the review process

Sprint 27 is the interesting comparison. It found that the class code protected
nothing and fixed that completely — grant, binding, expiry, spend-on-use, tests
at the token layer. Every one of those was right. And the credential the whole
mechanism protects was thirteen and a half thousand values wide, which nothing
in that sprint looked at, because the finding was about possession and I audited
possession.

**Enforcing a credential correctly and the credential being worth anything are
separate questions, and fixing one reads as having fixed both.** That is the
lesson worth keeping: when a sprint hardens the path to a secret, ask in the
same breath how large the secret is and what it costs to guess.

The second finding is the fifth instance of the pattern this review has kept
finding — a word doing work the system could not support. "Certified" (25),
"fall and spring windows" (27), "aggregates only" (26), "scheduled purge" (30).
Two were fixed by changing the word, two by building the state. The test each
time is which the product actually needs.

- **The route and action inventory is still not complete.** It has now found
