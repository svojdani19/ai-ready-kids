**Scope.** Route and action inventory, continued. Both findings correct. The
first is a mutation nobody could see, which is why nobody looked at it.

## Finding 1 — an unused action that deleted a child's work

Three places promise the same thing about replaying a finished mission: the
player itself — *"your badge stays, and nothing you tap now gets recorded"* —
the README, and several review records.

`replayMission` did the opposite. It called `requirePlayableMission`, which a
completed mission passes **by design** (sprint 27 made replay a deliberate
exception so withdrawing an assignment cannot delete access to finished work),
and then called `resetAttempt`, which drops the whole row: completion, path,
evidence, and the badge with it. If the assignment had since been withdrawn, the
child also lost access to the mission entirely.

No button called it. It was exported from a `"use server"` module, which makes
it a public endpoint regardless.

**It is deleted**, with a comment where it stood explaining what it did and why
replay means what the copy says. `resetAttempt` stays in the repository for
tests and for any future support tool — which, if it is ever built, has to be an
authorised adult operation with confirmation and an audit entry, not something a
child's browser can invoke.

Two tests hold it: no student action may reference `resetAttempt` at all, and a
completed mission survives a full replay and a direct write attempt with
identical `completed_at`, path and evidence.

## Finding 2 — the class owner was taken on trust

`createClassAction` read `teacherId` from the form and passed it through. The
foreign key proves a user row exists; it says nothing about who they are.

So an administrator could create a class in their school owned by **a user id
from another school**. `listClassesForTeacher` then handed that outsider the
class on their overview and mission library — its name, join code, student
count and aggregate evidence — while `canTeachClass` denied them the class page,
because that rule *does* check school. A contradictory half-access nobody would
think to go looking for.

The action was also reachable by any teacher. Sprint 26 narrowed it so a teacher
could only name themselves as owner, which fixed the wrong half: the product
says administrators create classes, no screen offers it to teachers, and a
capability with no interface is still a capability.

### The fix, in three places

- **The action** is behind `requireAdmin` now, and resolves the requested owner
  before creating anything: the user must exist, be `role === "teacher"`, and be
  at the administrator's own school.
- **`createClass` enforces the same rule**, so no other caller can create a
  cross-school owner. This is the sprint 28 lesson applied without being
  prompted: the action is one caller, the repository is the boundary.
- **`listClassesForTeacher` is scoped by school as well as by teacher.** Defence
  in depth — if such a class ever existed, it must not surface with its join
  code attached.

## Found while verifying

The admin navigation still carried a **"→ Teacher view"** link. Sprint 26 made
the roster-bearing teacher pages teachers-only, so for three sprints that link
has been bouncing administrators straight back to the page they were on. Removed,

That is a small thing and worth recording anyway: a permission change left dead

## Tests

## What this says about the review process

The interesting part of finding 1 is that the defect was invisible to every
method used here so far. It was not on a page, so browser checks could not see
it. It was not called by anything, so reading the UI could not find it. It had
no test, because nothing exercised it. Its own access check *passed* — correctly,
under a rule sprint 27 deliberately introduced.

The only way to find it was to enumerate the exported actions and read each one
against what the product claims. That is the inventory I said in sprint 28 had
not been done, and this is the second sprint running where it has found
something. **An exported server action is a route.** It needs the same treatment
as a page, and being unreferenced makes it more suspicious rather than less,
because nothing is exercising it and nobody is looking at it.

Finding 2 is the third instance of a pattern now worth naming as a rule rather
than as a recurring surprise: **a foreign key is not an authorization check.**
It proves a row exists. Sprint 26 trusted `school_id` alone; sprint 28 trusted
that a student id and a class id belonged together; this one trusted that a user
id was a teacher here.

## Deliberately left

- **The inventory is still not complete.** It has now found something twice, and
  it stops when somebody has read every exported action and every route against
  what the product claims — not when the last finding is fixed.
- `simulateAttempt` still writes seed paths directly, and `enterDemo("student")`
  still writes a student session directly.
