# Sprint 75 — the switch that decides what children are offered, committed apart from its record

**Date:** 2026-08-29
**Reviewed against:** HEAD `96f67c5`
**Scope:** `setBenchmarkWindowAction` only, plus one narrow guard entry. No
sweep of the remaining configuration actions. No schema change, no student-data
field.

## The finding

`setBenchmarkWindowAction` wrote `schools.benchmark_window` and inserted
`benchmark.window` afterwards, as two commits. That setting decides — immediately
and school-wide — whether children may start or resume the fall form, the spring
form, or neither.

A failing audit insert could therefore leave a window opened, closed or switched
with no trustworthy record of who did it: children into an assessment outside
its administration period, a mid-form class stopped from resuming, or a cohort
moved between forms in a way that contaminates the report's fall-to-spring
comparison. That is benchmark integrity, not logging.

## The correction

Option validation and the **lapsed-subscription refusal both stay above the
transaction**, so neither takes a write lock. `setBenchmarkWindow` and the
`benchmark.window` audit are wrapped in `auditedWrite`. On failure:

> The check-in window was not changed. Children are still offered exactly the
> same check-in as before you pressed Save — the same fall form, spring form, or
> none at all — and this attempt started no child, stopped no child, and moved
> nobody to a different check-in. Try again.

It answers the question an administrator would otherwise have to go and ask a
classroom, and it does **not** claim the attempt was recorded, because the
rollback takes the audit row with it. No support promise.

`setBenchmarkWindow(` joins the consequential-write guard as **one** new entry,
for the same reason retention did: not destructive, not cosmetic. The expected
wrapped-action proof now names ten.

## Proof, through the exported action

Real admin session, real database, real `FormData`, and
`BEFORE INSERT ON audit_log WHEN NEW.action = 'benchmark.window' RAISE(ABORT)`.
Snapshots cover the complete school row, a second school, all classes, students,
attempts, benchmarks and audit rows — plus representative eligibility via
`nextBenchmarkFor` and `canTakeBenchmark`.

**Each transition on its own fresh fixture**, so they cannot mask each other:

| Transition | Asserted after the failure |
| --- | --- |
| **closed → fall** | a child with no benchmark record is still offered nothing (`next: null`, `pre: false`, `post: false`), **and the real exported `submitCheckInAnswer` refuses as that signed-in child** with `{ ok: false, error: "That check-in is not open." }`, writing no benchmark row |
| **fall → closed** | a child with an *incomplete* fall record is still `{ form: "pre", resuming: true }`, `pre` still eligible, and the unfinished record with its saved option byte-identical |
| **fall → spring** | fall remains the only eligible form; spring stays unavailable |

The closed → fall case signs in as the child, calls the endpoint, and signs the
administrator back in — the consequence is exercised, not mocked.

**Retry after dropping the trigger:** the school row differs in
`benchmark_window` and nothing else; eligibility becomes exactly
`{ next: { form: "pre", resuming: false }, pre: true, post: false }`; **opening a
window starts nobody** — no benchmark row for the fresh child, and classes,
students, attempts and benchmarks all byte-identical; exactly one new
`benchmark.window` audit against the seeded baseline, whose detail
`"Check-ins set to the fall window."` matches what the administrator was told;
and the other school keeps its own `pre` window.

**Existing refusals, behaviourally:** `""`, `"summer"`, `"PRE"`, `"1"`, `"null"`
each return *"Choose closed, fall or spring."*; a lapsed term returns the
subscription refusal and **not** the operational message. Both write nothing.

## Known gaps

- **Ten configuration actions still audit outside a transaction**:
  `updateSchoolAction`, `requestPlanChangeAction`, `addTeacherAction`,
  `reassignClassAction`, `createClassAction`, `addStudentAction`,
  `renameStudentAction`, `setAssignmentAction`, `completeCertificationAction`.
  Retention (74) and the check-in window (75) were pulled out of that set
  because each changes what happens to children school-wide. The remainder are
  additive or cosmetic single-row writes, and the guard deliberately does not
  flag them.
- **`setAssignmentAction` is now the closest call.** It decides which missions a
  class is offered, so it is the same *kind* of thing one class at a time —
  smaller blast radius, and out of scope here.
- **Failures still write nothing**, consistent with sprints 70–74.
- **The guard reads source text** and would miss a write reached through an alias
  or a helper.
- **A window change still cannot be undone by the product** if a child answers
  in the meantime. Atomicity means the switch and its record agree; it does not
  mean an accidentally-opened window can be rolled back after a class has
  started answering.
