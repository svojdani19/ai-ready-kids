# Sprint 48 — the Cancel that could not cancel

**Date:** 2026-08-28
**Scope:** the shared `ConfirmAction` component and its tests. No caller
contract changed.

## The finding

`ConfirmAction` guards archive, restore, delete, and the staff and class
actions. Once the confirm button was pressed it went `disabled`, and **Cancel
stayed live**. All Cancel did was `setConfirming(false)` — collapse the
interface. The server action carried on.

So an administrator could press **Delete permanently** on a class, have a second
thought, press **Cancel**, watch the confirmation disappear, reasonably conclude
they had stopped it — and find the roster, the mission history, the evidence and
both check-ins gone.

This is the worst kind of interface defect because it is not a failure to act.
It is **false reassurance at the exact moment doubt should be acted on**. A
control labelled Cancel that cannot cancel is worse than no control at all:
without it, the user knows they are committed and goes looking for a way to
recover. With it, they stop looking.

Two smaller defects in the same component: opening the confirmation unmounted
the focused launcher and put focus on nothing, and collapsing — after Cancel,
after an error, after success — left focus wherever that had dropped it. That is
sprints 45–47's defect class again, in the control that guards deletion.

## What changed

**Once the request is away, there is no Cancel.** It is replaced by
non-interactive text: **"Cannot be stopped now."** Not a disabled button, which
still reads as a control that might come back — a plain statement of fact.
Nothing about this component can recall a server action, so nothing about it
pretends to.

**No reopening or re-firing while pending.** The state stays `confirming` for
the duration, so the launcher does not exist to be pressed again, and the
confirm button is disabled. `disabled` alone was not enough — it only takes
effect after a re-render, and two clicks can land before one happens — so an
`inFlight` ref guards the handler as well. The action is called **at most once**
per confirmation.

**Focus enters the confirmation.** Opening it focuses the confirm button, which
carries the question as its `aria-describedby`, so the consequence is read with
the control rather than sitting beside it unassociated. It stays an **inline
two-step, not a modal** — no dialog semantics, nothing to dismiss by accident.

**Focus comes back on every exit.**

- **Cancel before submission** collapses and returns focus to the exact
  launcher, and **never calls the action**.
- **An expected `{error}`** collapses, preserves and announces the `role="alert"`
  message, and puts focus on the launcher — which is where recovering from it
  starts, with the alert beside it.
- **Success** restores focus to the launcher **only if it is still connected**.
  A delete revalidates the page and may take the whole row with it; focusing a
  detached node puts focus on nothing, which is the defect this exists to avoid.
- **Unmount** touches nothing at all.

A previous error is also cleared when the action is tried again, so a stale
alert cannot sit beside a fresh attempt.

## Tests

A new `tests/confirm-action.test.tsx`, eleven cases, driven by a **deferred
promise the test settles by hand** — so the pending state is inspected while the
action is genuinely in flight rather than guessed at with a timer.

**Six confirmed to fail against the old component** by stashing it: focus entry
with the accessible description, pre-submit Cancel returning focus without
calling the action, no operative Cancel while pending, error recovery with
announcement and focus, success recovery, and the quiet tone behaving the same.

Five pass either way, guarding what must not regress: single invocation under a
double press, no reopening while pending, error clearing on retry, unmount
safety, and no focus theft on first render.

**553 tests, up from 542.**

## Verified in the browser

**Admin, 1280×800 — archive and restore a class.** Opening the confirmation put
focus on *Archive class*, with the question as its accessible description and no
`role="dialog"` anywhere. Cancel returned focus to the exact *Archive* launcher,
visible, with the class still active. On a real confirm, a `MutationObserver`
watching the row through the transition recorded **"Cannot be stopped now"** and
a **disabled "Working…"**, and the marker for a live Cancel coexisting with the
pending state **never fired**.

**Teacher, 768×1024 — rotate a class code.** Focus entered *Change it* with the
question described. Cancel returned focus to *New code* and **the code did not
rotate**. On confirm, the pending text appeared with no live Cancel, the code
changed, and focus came back to the launcher. No horizontal overflow.

## Worth stating precisely

On the admin success path, focus returned to the launcher element — which React
had reused and **relabelled from "Restore" to "Archive"**, because the action
succeeded and the row's state changed. That is the right outcome rather than a
gap: focus stays exactly where the user left it, on the control now occupying
that position. It is worth naming because "restore focus to the launcher" and
"restore focus to a button with the same label" are not the same thing, and only
the first is achievable when the action changes what the row offers.

## Preserved

Server actions, entitlement enforcement, retention, audit behaviour, child-data
constraints, and the inline non-modal design. No caller changed: the
`action: () => Promise<void | { error?: string }>` contract is untouched.

## Observed, not changed

**A confirmed action still cannot be undone.** This sprint makes the interface
honest about that; it does not add an undo. For archive and restore that is
fine, since both are reversible by their opposite. For `deleteClassDataAction`
it means the only protection is the two-step and its wording. Whether a
school-facing product should offer a grace period on permanent deletion is a
product decision, not a component one.

## The lesson

**A control that cannot do what its label says is worse than its absence.** The
Cancel button was not decoration — it was doing active harm, by converting the
one moment a user reconsiders a deletion into a false belief that they had
stopped it. When an operation becomes uncancellable, the interface has to say so
plainly and take the control away, because a disabled-looking button still reads
as one that might come back.
