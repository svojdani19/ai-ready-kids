# Sprint 45 — Escape closed the menu and abandoned the user in it

**Date:** 2026-08-28
**Scope:** the keyboard-focus defect sprint 44 observed and reported. Shared
header only.

## The finding

With a desktop dropdown open and one of its links focused, pressing Escape hid
the menu and **left focus on that link** — still in the document, no longer
visible. The next Tab continued from a place the user could not see.

This is worse than it sounds for the people it affects. A sighted pointer user
never meets it. A keyboard or switch user meets it every time, and what they
experience is Tab landing somewhere arbitrary with no way to tell where they
are. For a school buyer running an accessibility assessment, "Escape closes the
menu" is not an answer on its own: **a dismissal that does not say where focus
went is not a way out**, it is a way to get lost.

## What changed

`useDismiss` now reports *why* it fired. The close callback takes a
`DismissReason` — `"escape" | "pointer" | "focus"` — and only Escape hands focus
back:

```ts
const dismiss = useCallback((reason: DismissReason) => {
  const hadFocus = Boolean(wrapper.current?.contains(document.activeElement));
  setOpen(false);
  if (reason === "escape" && hadFocus) button.current?.focus();
}, []);
```

Two guards, and both matter:

- **Reason.** Every other dismissal already leaves focus somewhere the user
  chose — on the link they followed, on what they clicked, on what they tabbed
  to. Pulling it back would be taking focus, not restoring it.
- **`hadFocus`.** Refocusing only when focus is actually inside the menu keeps
  this to the recovery case. If the user has already moved on, the thing being
  hidden is not what holds focus, and there is nothing to recover.

Each `NavMenu` closes over its own `button` ref, so a trigger gets its own menu
back and never a sibling's.

**No reopen loop.** The refocus lands on the trigger, which is inside
`wrapper.current`, so the `focusin` dismissal handler sees a target it contains
and does nothing. The click-outside and focus-out paths are otherwise unchanged.

## Tests

A new `tests/site-header.test.tsx`, jsdom and Testing Library, ten cases —
against the real component rather than the source, because **focus is behaviour**:
the question is where the browser puts it, not which line was written.

Four assert the fix and were confirmed to **fail without it**:

- Escape with a link focused returns focus to the trigger, with
  `aria-expanded="false"`, the link **not** focused and **not visible**;
- each trigger gets its own menu back, not a sibling's;
- the refocus does not reopen the menu, and a second Escape is a no-op;
- Escape still works the second time a menu is opened.

Six assert it does **not** over-correct, and pass either way — which is the
point, since a fix that grabs focus is as bad as one that strands it: choosing a
link, clicking outside, focus moving away on its own, and toggling the trigger
closed all leave focus where the user put it. Plus one structural case: all four
links reachable and labelled while open, and the blurb sprint 44 corrected
asserted where a buyer reads it.

**523 tests, up from 513.**

## Verified in the browser

**1280×800, keyboard only.** Trigger focused and opened; Tab reaches the links;
focus put on *Administrators*; Escape → menu hidden, `aria-expanded="false"`,
focus on the trigger and **visible**; Tab from there proceeds to the next visible
control, *See the demo*, in document order.

**768×1024.** Unchanged, as required. The desktop triggers are not rendered at
this width; the mobile panel opens from its own Menu button with ten links, and
closing it returns nothing to recover — **focus is on the Menu button itself,
visible and not stranded**, because the close is the toggle. No horizontal
overflow.

## Observed, not changed

**The mobile panel does not respond to Escape at all.** It never did — it is not
wired to `useDismiss` — and this sprint was asked to leave mobile behaviour
unchanged, so it is left. It strands nobody today, because the only way to close
it is the button that keeps focus. If Escape is ever added there, it needs the
same reason-aware treatment, and the close button is the trigger to return to.

## The lesson

**A dismissal is not finished until it says where focus went.** The Escape
handler was written to answer "is the menu open?" and it answered that
correctly; nobody asked "and where is the user now?". The same question applies
to every closable thing in this product — the `ConfirmAction` two-step, the
classroom-mode overlay, any future dialog — and it is invisible to anyone
testing with a mouse, which is exactly why it survived a browser check that
otherwise found it.

Worth noting for the loop itself: sprint 44 found this while checking something
else, reported it, and did not fix it. That was the right call for a copy-only
sprint, and it only stayed the right call because the next sprint picked it up.
