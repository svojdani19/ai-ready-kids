# Sprint 73 — the same operation, transactional on one path and not the other

**Date:** 2026-08-29
**Reviewed against:** HEAD `c65026b`
**Scope:** the three remaining irreversible or credential-changing actions, plus
a structural guard. No schema change, no student-data field, no telemetry.

## The finding

Sprint 71 made the **administrator's** code rotation atomic with its audit
entry, and left `rotateJoinCodeAction` — the **teacher's** rotation — untouched.
Same repository call, same credential consequence, same audit action string, and
it is the path teachers actually use: a code goes on a whiteboard, so needing a
new one is an ordinary Tuesday. One of two identical paths was fixed.

Two more of the same shape, both irreversible:

| Action | Mutates | Lost audit means |
| --- | --- | --- |
| `rotateJoinCodeAction` (teacher) | `rotateJoinCode` | a credential changed with no record of it |
| `removeStudentAction` | `deleteStudentFromClass`, cascading to every attempt and check-in | a child's records gone with no answer to "who removed them, and when" |
| `removeStaffAction` | `deleteUser`, cascading to their certification | an account and its orientation record gone, unrecorded |

Fifteen actions in total still audited outside a transaction. These three were
selected because their failure cannot be undone by trying again; the other
twelve are single-row configuration writes, named as a remaining gap below.

## The correction

Each wraps its mutation and audit in `auditedWrite`, and returns a calm inline
error naming the state that did not change:

| Operation | On failure |
| --- | --- |
| Teacher rotation | *"Room 12 did not get a new code. The current code still works and nobody has been signed out. Nothing was changed. Try again."* |
| Remove student | *"That student was not removed, and **no records were deleted**: they are still on Room 12's roster with their mission history and check-ins exactly as they were. Try again."* |
| Remove staff | *"…They still have their account and their orientation record, and no class changed hands. Nothing was changed. Try again."* |

The **mismatched-pair refusal keeps its own message.** A student id that is not
on the authorising class throws before anything is attempted, so it is not an
operational failure and does not get the operational message.

### A structural guard, not another list

Sprint 71's promise guard named four actions, so a fifth would have slipped past
— which is exactly what had happened to the teacher rotation. The new guard keys
on the **repository call** instead:

```
deleteClass(  deleteStudentFromClass(  deleteUser(  rotateJoinCode(
archiveClass(  restoreClass(  setAcademicDates(
```

Any exported action that performs one of these **and** audits must use
`auditedWrite`. A new action that deletes a class is caught without anyone
remembering to add it. A companion test asserts the sweep is finding the eight
actions that exist, so a guard that scanned nothing could not pass silently.

## Failing-before and mutation checks

Reverting `removeStudentAction` to mutate-then-audit:

```
× removing a student: an audit failure deletes no records
× removing a student: the retry removes them and audits exactly once
× a mismatched student and class still refuses, and audits nothing
× pairs every consequential write with auditedWrite      ← the structural guard fires
```

Then each audit broken **on its own**, never in a batch:

```
break only teacher rotate audit  -> 2 failing tests
break only student removal audit -> 2 failing tests
break only staff removal audit   -> 2 failing tests
```

Two each: the audit-failure test and the retry test for that operation, and no
others.

The retry tests assert the mutation itself, not its precondition — sprint 71's
correction applied at the point of writing. Rotation requires a **changed**
`join_code` with every other column identical; student removal captures the
child's id **before** the delete and asserts their attempts are gone by that
literal id (sprint 67's lesson); staff removal compares the whole `users` table.


One pre-existing **source-position** test broke and was replaced rather than
patched: `access-control` asserted `if (!removed)` appeared before `recordAudit`
in the action body. `recordAudit` is no longer a string in that body, so the
assertion could only ever go stale; the property it stood for — a mismatched
pair writes no audit — is now behavioural.

## Correction to earlier sprints' demo-restore claims

Checking the demo afterwards, its counts did not match what sprints 70–72
recorded (884 attempts / 134 benchmarks / 53 assignments). They are now
**1078 / 129 / 65**.

Traced rather than assumed. A fresh seed today produces exactly
`students=90 attempts=1078 benchmarks=129 assignments=65 audit=6` — the live
file matches a current seed exactly. `data/airk.db` was rewritten at **10:26**,
which is when I restarted the dev server during sprint 70's acceptance
correction.

**The cause was my sprint-70 restore.** I replaced the database file while a
server held it open; the copy captured the main file without the pages that
server still had in its WAL, so the restarted process read the database as empty
and `seedIfEmpty` re-seeded it from today's content. Sprint 70's review already
warned that "verifying a restore with `node` proves the file, not the process" —
this is that hazard doing more than leaving a stale process.

**What is true now:** the demo is a clean, current-content seed — Brightwood,
2025-2026 / 2025-08-25 / 2026-06-12, term 2025-08-18 → 2026-09-01, whole-school
plan, 120 seats, retention 12, the four original join codes, nothing archived,
no assignment notes, and the six seeded audit actions in order. Nothing was
lost: it is gitignored fictional demo data, and the newer vintage reflects
missions added since the old backup was taken.

**What was wrong:** sprints 70, 71 and 72 each state "demo restored exactly" and
quote 884 / 134 / 53. Those numbers were accurate when written and stopped being
the demo's content at 10:26. The restores themselves did what they claimed
within each sprint; the file-copy method in sprint 70 is what broke, and no
sprint since has used it — sprints 71, 72 and 73 all arm and drop triggers in
place.

## Known gaps

- **Twelve configuration actions still audit outside a transaction**:
  `updateSchoolAction`, `requestPlanChangeAction`, `setRetentionAction`,
  `setBenchmarkWindowAction`, `addTeacherAction`, `reassignClassAction`,
  `createClassAction`, `addStudentAction`, `renameStudentAction`,
  `setAssignmentAction`, `completeCertificationAction`. Each is a single-row
  write whose loss cannot leave a half-finished state, which is why they were
  not in this sprint — but the page's promise covers them, and the structural
  guard deliberately does not flag them, because keying it on "any write at
  all" would have made it a list again.
- **Failures still write nothing**, consistent with sprints 70–72.
- **The guard reads source text.** It would miss a consequential write reached
  through an alias or a helper, and it cannot see a repository function that
  becomes destructive later.
